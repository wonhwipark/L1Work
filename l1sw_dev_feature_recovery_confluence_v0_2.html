L1 SW DEVELOPMENT PROCESS · CONCEPT v0.2

l1sw-dev-feature × L1 Recovery
표준 피처 개발 프로세스 설계 제안

Crash · Stuck · WDT 같은 L1 문제를 AI로 분석한 뒤, 그 결과를 실제 제품 피처로 개발·검증·종료하기까지 담당자마다 같은 절차와 같은 산출물을 사용하도록 만드는 Feature Lifecycle Orchestrator 설계안입니다.

핵심 아이디어: L1 Recovery는 “문제와 Recovery 후보”를 만들고, l1sw-dev-feature는 그 후보를 “검증 가능한 개발 계약”으로 승격해 SRS → HLD → 구현 → 검증 → 환류를 끝까지 관리한다.
01 · 배경

왜 새로운 스킬이 필요한가

현재도 코드 분석, HLD 작성, 코드 구현, Fix 이력 검색, 지식 관리 등 각 구간을 잘 수행하는 스킬은 존재합니다. 문제는 각 스킬이 자기 구간만 알고 있다는 점입니다. 그래서 “처음 요구한 내용이 실제 코드에 반영됐는가?”, “그 변경이 어떤 시험으로 검증됐는가?”, “이번 과제에서 배운 것이 다음 과제에 재사용되는가?”를 하나의 흐름으로 답하기 어렵습니다.

현재 잘하는 것하지만 남아 있는 문제
코드 분석이 분석이 어떤 Feature 요구 때문인지 연결이 약함
HLD 작성설계가 실제 구현·검증까지 완료됐는지 한눈에 보기 어려움
구현 / Fix변경의 원 요구·설계 근거를 나중에 다시 찾아야 함
UT / 로그 검증무엇을 어떤 기준으로 검증해야 하는지 담당자마다 달라질 수 있음
지식 관리이번 과제에서 무엇을 배웠고 무엇을 등록해야 하는지 별도 정리가 필요함
따라서 부족한 것은 “분석 능력”이 아니라 “개발 생명주기를 연결하는 공통 Control Plane”입니다. l1sw-dev-feature는 모든 기능을 다시 만드는 Mega Skill이 아니라, 단계(Stage), 완료 조건(DoD), 승인 Gate, 추적성, 다음 동작을 관리하는 워크플로우 계층이어야 합니다.
초보자 설명 여러 전문가가 각각 좋은 일을 하고 있어도, 프로젝트 매니저가 없다면 “누가 무엇을 끝냈고 다음에 무엇을 해야 하는지”가 흐려질 수 있습니다. l1sw-dev-feature는 코드를 직접 잘 고치는 전문가가 아니라, 각 전문가가 같은 순서와 같은 기준으로 일하도록 만드는 프로젝트 실행 엔진에 가깝습니다.
02 · 목적

l1sw-dev-feature가 달성해야 할 것

담당자 편차 축소

누가 맡아도 같은 단계, 같은 질문, 같은 완료 기준을 사용합니다.

요구 → 검증 추적

“이 요구가 실제로 구현되고 시험됐는가?”를 레코드 하나에서 확인합니다.

산출물 표준화

SRS/HLD/구현계획/검증표/종료보고를 동일 데이터에서 생성합니다.

과제를 통한 자동 학습

과제 종료 시 새 절차, 실패 모드, 구현 패턴을 지식 후보로 환류합니다.

목표는 문서를 더 많이 만드는 것이 아닙니다. 하나의 Feature Record를 단계별로 채우고, 필요한 문서는 그 레코드에서 자동 생성되게 하는 것이 목표입니다.
03 · 전체 구조

L1 Recovery와 Feature 개발의 연결

L1 Recovery 스킬의 출력은 바로 SRS가 되기보다 먼저 Feature Intake를 거치는 것이 안전합니다. Recovery 분석 시점의 일부 내용은 아직 확정된 요구가 아니라 원인 가설 또는 해결 후보일 수 있기 때문입니다.

Gate 추가 없음
→
S1 · SRS 무엇이 달라져야 하는지
관측 가능한 요구 확정
→

→
S3 · 구현 승인 범위 내 코드 변경
Diff / Change ID 연결
→
S4 · 검증 UT / Log / Fault Injection

→
S5 · 환류 새 절차·실패 모드·패턴을

S0는 “새로운 승인 단계”가 아닙니다. L1 Recovery 출력의 Fact·Hypothesis·Candidate를 분리하고 Feature 입력 형식으로 정리하는 전처리 단계입니다. 첫 사람 승인은 기존처럼 G-SRS에서 수행합니다.
04 · 역할 경계

Recovery Candidate와 Feature Requirement는 다르다

L1 Recovery가 만드는 것

  • 어떤 현상이 발생했는가
  • 어떤 증거가 있는가
  • 가능한 Root Cause는 무엇인가
  • 어떤 Recovery 방법이 후보인가
  • 어떤 부작용 또는 Open Item이 있는가

CANDIDATE 아직 설계 승인 전

l1sw-dev-feature가 만드는 것

  • 제품 동작이 어떻게 달라져야 하는가
  • 그 변화가 외부에서 어떻게 관측되는가
  • 어떤 절차/모듈이 소유하는가
  • 무엇을 구현하고 무엇으로 검증하는가
  • 언제 “완료”라고 판정할 수 있는가

FEATURE CONTRACT 승인 가능한 개발 기준

예시 “TxSwitchMngr가 stuck해서 WDT가 발생한 것 같다 → 일정 시간 후 reset하자”는 좋은 Recovery 후보입니다. 하지만 Feature Requirement가 되려면 “어떤 상태를 stuck으로 판정하는지”, “정상 지연과 어떻게 구분하는지”, “reset 후 무엇이 정상 복귀 증거인지”까지 정의되어야 합니다.
05 · 핵심 데이터 모델

Feature의 중심은 문서가 아니라 Behavior Delta

Behavior Delta(BD)는 “이 과제를 적용하면 시스템 행위가 어떻게 달라지는가”를 한 건 단위로 기록한 것입니다. SRS, HLD, 구현, 검증이 각각 다른 문서에서 별도 ID를 만들기보다, 같은 BD가 단계별 필드를 얻어가는 방식을 권장합니다.

기본 형식 어떤 조건에서(Condition) · 지금은 어떻게 동작하고(Current) · 앞으로는 어떻게 동작해야 하며(Target) · 무엇을 보면 성공 여부를 알 수 있는가(Observable) 
behavior_delta:
  id: BD-003

  # S0 · Recovery 출처
  recovery_source: RC-001
  failure_fact_refs: [FACT-001, FACT-004]

  # S1 · 요구
  condition: "ULCA active + TX switch pending"
  current_behavior: "재진입 CMD 발행"
  target_behavior: "재진입 CMD 억제"
  observable:
    type: MESSAGE
    anchor: "TX_SWITCH_REQ 이후 CMD_TX_SWITCH 미발행"

  # S2 · 설계
  procedure: "proc_periodic_tx_switch"
  owner_module: "TxSwitchMngr"
  design_intent: "pending 상태 재진입 방지"

  # S3 · 구현
  code_refs: ["tx_switch_mngr.cpp::handleReq"]
  change_id: "CL / PR / commit"

  # S4 · 검증
  evidence:
    - {type: UT, result: PASS}
    - {type: FAULT_INJECTION, result: PASS}
    - {type: LOG, result: PASS}

  # S5 · 환류
  knowledge_candidates:
    - FAILURE_MODE
    - IMPLEMENTATION_IDIOM
초보자 설명 SRS 문서, HLD 문서, 시험 문서를 서로 번역해서 연결하는 대신, 같은 BD-003에 요구·설계·코드·시험 정보를 차곡차곡 붙입니다. 그러면 BD-003을 읽는 것 자체가 추적성입니다.
06 · Recovery Feature 표준 관점

Crash / Stuck / WDT는 공통 질문을 강제할 수 있다

Recovery 기능은 일반 Feature보다 공통 구조가 뚜렷합니다. 따라서 담당자가 아래 관점을 반드시 검토하게 하면 경험 차이를 크게 줄일 수 있습니다.

BD 유형필수 질문예시
Detection고장을 무엇으로 검출하는가?Progress counter 정지, timeout, state mismatch
Qualification진짜 장애와 정상 지연을 어떻게 구분하는가?연속 N회 미변경 + procedure 상태 확인
Recovery Action무엇을 reset/reinit/retry 하는가?Sub-state 재초기화, command retry
Guard / Safety정상 상황에서 잘못 Recovery하지 않도록 무엇을 막는가?진행 중 중요 procedure에서는 trigger 금지
EscalationRecovery가 실패하거나 반복되면 다음 단계는?Local recovery → subsystem recovery → 상위 recovery
Post-validationRecovery 후 정상 복귀를 무엇으로 확인하는가?정상 state + 정상 message sequence 재개
Diagnostics다음 분석을 위해 무엇을 남기는가?Pre-recovery state snapshot, reason code, counter
이 7개가 반드시 7개의 BD가 되어야 한다는 의미는 아닙니다. 작은 Feature에서는 합칠 수 있습니다. 중요한 것은 “이 관점을 검토했는가”를 자동 체크하는 것입니다.
07 · 단계 모델

S0 ~ S5 표준 개발 프로세스

단계목적주요 입력핵심 산출/필드완료 조건(DoD)Gate
S0 Intake Recovery 결과 정규화 Facts / Hypothesis / Recovery Candidate Feature 후보, BD 후보, Open Item Fact와 가설이 구분되고 출처가 존재 없음
S1 SRS 무엇이 달라져야 하는지 확정 BD 후보, 요구 원문, 규격/Issue Condition / Current / Target / Observable 모든 BD가 관측 가능하고 근거가 있음 G-SRS
S2 HLD 어떻게 달라질지 설계 코드 사실, 기존 HLD, 지식 Procedure / Owner / Design Intent / MSC 모든 BD가 절차와 소유 모듈에 매핑 G-HLD
S3 구현 승인된 설계를 코드로 반영 HLD Delta, Gap, 범위 Code refs / Diff / Change ID 모든 구현 BD가 변경 식별자와 연결 G1 / G2 재사용
S4 검증 S1에서 정한 관측 기준으로 증명 UT, 로그, Fault Injection Evidence / Verification Matrix / Verdict 모든 AC/BD가 PASS 또는 승인된 WAIVED G-VER
S5 종료·환류 과제 종료 및 지식 재사용 완료 BD, 증거, 변경 이력 Closeout / Knowledge Candidate 모든 후보가 승인/거절 판정을 받음 G-CLOSE
08 · 산출물

09 · 검증

Recovery Feature는 “고장이 안 났다”로 검증하면 부족하다

Crash/Stuck/WDT 개선은 정상 케이스만 확인해서는 충분하지 않습니다. 가능하면 Fault Injection을 정식 Evidence 타입으로 두고 아래 네 축을 확인해야 합니다.

1. Trigger / Detection

의도한 Failure를 정확한 조건에서 검출하는가?

2. Recovery Effectiveness

Recovery 후 실제로 정상 procedure/state로 복귀하는가?

3. Recovery Safety

정상 상황에서 오검출 또는 불필요한 Recovery가 없는가?

4. Repetition / Escalation

반복 장애 또는 Recovery 실패 시 상위 정책이 동작하는가?

AC-R01  Stuck condition 강제 발생
        → detection <= N ms
        → recovery action 1회
        → 정상 state/message sequence 복귀

AC-R02  정상 processing delay 발생
        → recovery trigger 없음

AC-R03  Recovery action 자체 실패 유도
        → escalation policy 동작

AC-R04  연속 fault 반복
        → resource leak / deadlock / state corruption 없음
핵심 원칙: 관측할 수 없는 요구는 승인하지 않는다. “정상 동작할 것”, “안정성 향상” 같은 문장은 S1에서 구체적인 Message / State / Log / Timing / UT assertion으로 바뀌어야 합니다.
10 · 학습 데이터

단계별로 필요한 지식과 과제가 남기는 지식

단계들어가는 지식과제 종료 시 남길 수 있는 지식
S0 Failure signature, 유사 Crash/Stuck/WDT, 과거 Fix precedent 새 Failure signature
S1 Recovery requirement pattern, Detection/Guard/Escalation 관측 패턴 새 Observable / Requirement pattern
S2 Message procedure, State machine, Ownership, concurrency invariant 새 Recovery procedure / MSC
S3 Implementation idiom, 금지 패턴, 과거 승인 Fix 새 Recovery implementation idiom
S4 Fault injection pattern, 정상 baseline, Failure mode 새 Injection pattern / Failure mode
S5 Knowledge promotion rule 검증 완료된 조직 Knowledge
과거 Fix는 정답이 아니라 참고 근거입니다. p4-fix-kb 같은 과거 변경 이력은 유사 구현을 찾는 데 매우 유용하지만, 현재 코드/로그/빌드 조건과 다시 맞는지 확인한 뒤에만 이번 설계 근거로 승격해야 합니다.
초보자 설명 “예전에 이렇게 고쳤으니 이번에도 똑같이 고친다”가 아니라, “예전에 이런 해결 패턴이 있었으니 현재 상황에서도 성립하는지 확인해 보자”가 맞습니다.
11 · 스킬 역할 분담

l1sw-dev-feature는 Mega Skill이 아니다

12 · 승인 신선도

승인 후 내용이 바뀌면 승인은 자동으로 STALE되어야 한다

프로세스에서 자주 생기는 구멍은 “승인받은 뒤 중요한 내용을 수정했는데 승인 상태는 그대로 남아 있는 경우”입니다. 이를 막기 위해 승인 대상 필드의 Digest를 저장하고 매번 다시 계산합니다. 

G-SRS APPROVED
  └─ BD-002 target 수정
      → G-SRS = STALE → 재승인 필요

G-HLD APPROVED
  └─ procedure / design_intent 수정
      → G-HLD = STALE

G-VER APPROVED
  └─ 승인 후 code diff 변경
      → G-VER = STALE

title / note 같은 무관 필드만 변경
      → 기존 승인 유지
이 기능이 없으면 Gate는 곧 형식적인 체크박스가 됩니다. 반대로 무관한 필드까지 모두 재승인시키면 승인 피로가 생기므로, Gate별로 “승인에 영향을 주는 필드”만 명확히 정의해야 합니다.
13 · 담당자 UX

담당자가 알아야 할 명령은 최소화한다

담당자가 “지금 code-analyzer를 불러야 하나, hld-composer를 불러야 하나?”를 고민하게 되면 표준 프로세스의 장점이 줄어듭니다. 담당자가 만지는 표면은 l1sw-dev-feature 하나여야 합니다. 

feature new
feature import-recovery
feature status
feature next
feature approve
feature verify
feature close
예시
사용자:
"이 L1 Recovery 결과로 피처 개발 시작해줘"

출력:
FEATURE  FT-TX-WDT-004
SOURCE   REC-WDT-017
STAGE    S1 REQUIREMENT

BD       7 candidates
         5 ready / 2 incomplete

BLOCKING
- BD-004: recovery trigger observable 없음
- BD-006: escalation 기준 미정

NEXT
- 위 2개 항목 보완
- 완료 후 G-SRS 승인
초보자 설명 사용자는 “다음에 무슨 스킬을 실행해야 하지?”를 외울 필요가 없습니다. 현재 상태와 다음 한 단계만 알면 됩니다. 내부 라우팅은 l1sw-dev-feature가 담당합니다.
14 · 권장 입력 계약

L1 Recovery → Feature Dev Handoff 형식

두 스킬 사이의 경계를 안정화하려면 자연어 문서만 넘기기보다 recovery_feature_handoff.yaml 같은 정형 계약을 두는 것이 좋습니다. 

recovery_case:
  id: REC-WDT-001
  symptom: WDT

facts:
  - id: FACT-001
    statement: "..."
    evidence: ""

hypotheses:
  - id: HYP-001
    statement: "TxSwitchMngr state progression stuck 가능"
    confidence: MEDIUM

failure_model:
  trigger: "..."
  failed_state: "..."
  propagation: "..."
  detection_anchor: "..."

recovery_candidates:
  - id: RC-001
    mechanism: "..."
    trigger_condition: "..."
    guard_condition: "..."
    expected_behavior: "..."
    possible_side_effects: []
    escalation_policy: "..."
    confidence: MEDIUM

observables:
  - {type: STATE, anchor: "..."}
  - {type: MESSAGE, anchor: "..."}

constraints:
  recovery_latency_budget: "..."
  reentrancy: "..."
  concurrency: "..."
  build_option: "..."

open_items: []
가장 중요한 규칙: Fact · Hypothesis · Recovery Candidate를 섞지 않습니다. 특히 Hypothesis를 Feature Requirement로 자동 승격하지 않습니다.
15 · 도입 전략

처음부터 모든 것을 자동화하지 않는다

버전구현 범위검증하고 싶은 것
v0.1 Recovery Handoff import + BD + Stage/Gate/DoD + SRS/Status 데이터 모델이 실제 L1 Recovery Feature를 표현할 수 있는가
v0.2 코드/HLD/Knowledge/검증 스킬 위임 + Verification Matrix 실제 Feature 개발을 끝까지 연결할 수 있는가
v0.3 자동 Routing + Closeout Learning + 여러 Feature 상태 집계 팀 규모로 확장해도 담당자 사용성이 유지되는가
권장 파일럿: 현재 진행 중인 Crash/Stuck/WDT 사례 1건을 역등록합니다. 신규 과제를 기다리지 않고 기존 분석·설계·구현·검증 결과를 S0→S5에 역으로 넣어 봅니다. 채워지지 않는 필드가 바로 현재 데이터 모델 또는 프로세스의 구멍입니다.
16 · 성공 기준

이 스킬이 실제로 가치가 있는지 어떻게 판단할까

100%승인 Feature의 BD가 검증 Evidence와 연결
0건원 요구 없이 존재하는 구현 변경
0건Observable 없이 승인된 Recovery 요구
1 화면현재 단계·Blocker·Next Action 확인
  • 담당자가 바뀌어도 동일 Feature를 이어서 진행할 수 있는가
  • SRS 요구 하나를 선택하면 설계·코드·시험 Evidence까지 따라갈 수 있는가
  • 현재 Blocker를 담당자가 별도 설명하지 않아도 시스템이 계산하는가
  • 과제 종료 후 새 지식 후보가 자동으로 도출되는가
  • 과거 Fix를 그대로 복제하지 않고 현재 Evidence와 비교해 사용하는가
실패 기준도 미리 정합니다. feature status가 담당자가 이미 알고 있던 내용을 보기 좋게 다시 보여주는 수준이라면 충분하지 않습니다. “어느 BD가 어떤 이유로 막혔는지”와 “다음 무엇을 해야 하는지”를 결정형으로 알려줘야 합니다.
17 · 기대 효과

궁극적으로 얻고 싶은 변화

현재목표 상태
담당자가 자신의 방식으로 SRS/HLD/검증 수행Stage·Gate·DoD가 동일하고 산출물이 자동 표준화
문서와 코드가 시간이 지나며 어긋남BD에 설계·코드·Evidence가 함께 연결
Recovery 설계가 경험 많은 담당자 의존Detection/Guard/Escalation 등 공통 사고 프레임 제공
과거 Fix가 개인 기억에 의존Reference precedent로 검색하고 현재 Evidence로 재검증
과제 종료 후 지식 정리가 별도 업무S5에서 지식 후보를 자동 추출하고 승인만 수행
팀장이 상태를 담당자에게 물어 취합Feature State에서 Blocker와 Next Action을 동일 방식으로 계산
최종적으로 l1sw-dev-feature는 “문서를 작성하는 AI 스킬”이 아니라 “L1 Feature 개발 방법을 실행 가능한 프로세스로 만드는 스킬”이 되어야 합니다.
18 · 용어 정리

처음 보는 사람을 위한 핵심 용어

용어쉽게 설명하면
SRS무엇을 만들어야 하는지를 정리한 요구 명세
HLD어떤 구조와 절차로 만들 것인지 정리한 상위 설계
Behavior Delta (BD)Feature 적용 전후에 시스템 행위가 어떻게 달라지는지 기록한 한 건
Observable변경 성공 여부를 실제로 확인할 수 있는 메시지·상태·로그·타이밍 등
Gate사람이 승인해야 다음 단계로 넘어갈 수 있는 지점
DoD“이 단계가 끝났다”고 판정하기 위한 객관적 완료 조건
Fault Injection장애 조건을 의도적으로 만들어 Recovery 동작을 검증하는 방법
Escalation작은 Recovery가 실패했을 때 더 큰 Recovery 단계로 올리는 정책
SSOT같은 사실을 여러 곳에 중복 저장하지 않고 하나를 공식 원본으로 사용하는 원칙
STALE Approval승인 후 승인 대상 내용이 바뀌어 기존 승인이 더 이상 유효하지 않은 상태
Closeout / 환류과제를 끝내면서 배운 것을 다음 과제에서 쓸 수 있는 조직 지식으로 남기는 단계
19 · 권고 결론

다음 설계 작업의 우선순위

지금 단계에서는 SKILL.md 전체를 먼저 만드는 것보다 두 데이터 계약을 먼저 고정하는 것이 중요합니다. 데이터 모델이 맞으면 SRS/HLD/구현/검증 workflow는 그 위에 안정적으로 올라갈 수 있습니다.

1순위 · recovery_feature_handoff.yaml

L1 Recovery에서 Feature Dev로 넘길 Fact / Hypothesis / Candidate / Observable / Constraint 계약

2순위 · behavior_delta.yaml

S0~S5 동안 하나의 BD가 어떤 필드를 얻고 어떤 Gate/DoD를 만족해야 하는지 정의

권장 검증 방법 현재 개발 중인 L1 Crash/Stuck/WDT 실제 사례 하나를 선택해 기존 결과를 역등록하고, 두 데이터 계약만으로 S0→S5를 재구성할 수 있는지 확인합니다. 재구성되지 않는 지점이 다음 버전의 설계 입력입니다.
