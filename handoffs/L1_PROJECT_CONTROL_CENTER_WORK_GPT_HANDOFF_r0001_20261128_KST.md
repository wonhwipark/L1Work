# 업무 GPT · Project Control Center 구축 인계서

- 문서 버전: r0001
- 작성일: 2026-11-28 KST
- 수신: 업무 GPT
- 목적: 모바일 GPT의 `00.Project Control Center`와 같은 역할을 업무 환경에 구성
- 상태: 구축 요청 초안 / 업무 환경 조사 및 적용 대기

## 1. 구축 배경 및 목표

현재 모바일 GPT에서는 `00.Project Control Center`를 중심으로 여러 프로젝트의 개발, 리뷰, 배포, 인계 및 미해결 업무를 통합 관리하고 있음. 사용자는 새 대화창에서 전체 현황을 조회한 뒤 필요한 항목을 선택하여 심층 논의를 진행함.

업무 GPT에서도 동일한 운영 경험을 제공하고자 함. 단, 기존 개별 프로젝트를 물리적으로 합치거나 별도의 실행 엔진을 새로 개발하는 것이 목적은 아님. 기존 프로젝트·스킬·Work·결과 저장 구조를 유지하면서 상위 관리 창구를 하나로 통합하는 것이 목표임.

**최종 사용자 경험:** 업무 GPT의 Control Center에서 `전체 현황`을 요청하면 실제 업무 환경의 프로젝트별 최신 상태를 확인하고, 특정 항목에 대한 후속 분석·검토 또는 개별 프로젝트 인계를 이어갈 수 있어야 함.

## 2. 관리 대상 후보

아래는 모바일 GPT에서 관리 중인 업무를 기준으로 한 후보 목록임. 업무 GPT는 실제 프로젝트 목록과 관리 원본을 조사하여 명칭·소유자·중복 여부를 확정할 것.

| 관리 영역 | 주요 대상 |
|---|---|
| CoWork & Core / Skill Engineering | 스킬 개발·버전·검증·배포·협업 관리 |
| L1 Knowledge | l1-knowledge-updater, Source Map, Module·Feature·Procedure·Scenario·Issue |
| L1 Recovery | l1-channel-recovery, 원인 규칙·잔존 경로·검증 결과 |
| L1 Workspace | Viewer, Ledger Kernel, Work Evidence, 개인 Knowledge |
| 분석 공통 스킬 | Code Analyzer, Doc Converter, Fix Analyzer, Fix Workflow |
| 운영 기반 | Skill Updater, Job List, Runner/Worker, Agent MCP |
| L1 TL Management | 담당 업무, 이슈, 주간보고, 우선순위 및 사용자 조치 |
| AI Research / 기타 | 업무 환경에서 실제 관리하는 연구·기타 프로젝트 |

개인 투자 등 업무 범위 밖의 프로젝트는 기본적으로 제외하며, 업무 대상의 실제 범위는 사용자와 확인할 것.

## 3. 통합 운영 구조

```text
사용자
  └─ 00.Project Control Center (업무 GPT)
       ├─ 전체 현황 / 오늘 업무 / 스킬·실행·인계 현황
       ├─ 기존 프로젝트별 상태 및 근거 조회
       ├─ 선택 항목 심층 검토 / 다음 조치 판단
       └─ Context Handoff → 개별 프로젝트 / 기존 Work
                                └─ 실제 분석·개발·검증·결과 기록
       ← 최신 CURRENT / Work / Receipt / Result 조회
```

Control Center는 관리·판단·탐색의 진입점이며, 개별 프로젝트는 자신의 상세 설계와 실제 산출물의 소유권을 유지함. 단순 질의와 짧은 심층 논의는 Control Center에서 계속 진행할 수 있음. 장기 설계·구현·시험이 필요할 때만 별도 대화 또는 기존 Work로 분리하는 것을 기본 운영 방식으로 함.

## 4. 기존 정보 소스 조사 및 재사용

| 정보 소스 | 확인 사항 |
|---|---|
| 프로젝트 목록 / CURRENT / Dashboard | 관리 대상, 진행 상태, 최신 원본 위치 |
| Work Ledger / L1 Workspace | Work ID, 소유자, 상태, 근거 및 결과 링크 |
| 설치 스킬 메타데이터 / 실행 영수증 | 게시 버전과 실제 활성 버전, 실행 지문, 검증 결과 |
| Job List / Runner / Worker | Job ID, Run ID, 실행 상태, 산출물·실패 원인 |
| 기존 인계서 / TODO / 리뷰 결과 | 인계 리비전, 적용 여부, 미해결 과제, 다음 조치 |
| 기존 Reader / MCP | 실제 읽기 가능 범위, 권한, 응답 한도, 조회 실패 사유 |

동일 정보를 별도 파일·DB에 중복 축적하지 말고 가능한 한 원본을 참조할 것. 통합 인덱스가 필요하다면 원본 식별자·경로·갱신 시각·상태의 최소 정보만 유지하는 방안을 먼저 검토할 것. 원본과 집계가 충돌하면 원본 증거를 확인하고 불일치를 표시할 것.

모바일 측 참조 저장소(업무 GPT의 접근 가능 여부는 미확인):
- https://github.com/wonhwipark/L1Work
- https://github.com/wonhwipark/CoWork-Skill-Collab

업무 원본·상세 로그·소스코드·민감한 업무 정보는 승인된 업무 환경 안에 유지. 외부 저장소나 모바일 GPT로 자동 복제하지 말 것.

## 5. 프로젝트 지침 권장 초안 (복사하여 사용 가능)

> 너는 업무 GPT의 00.Project Control Center임. 전체 업무 프로젝트, 스킬 개발·검증·배포, 실행 결과, 인계 및 미해결 업무를 통합 관리하는 컨트롤 타워 역할을 수행할 것.
>
> 조회 요청마다 사용 가능한 최신 원본을 읽기 전용으로 확인하고, 프로젝트별 목적, 상태, 우선순위, 차단 사항, 다음 조치, 담당자/Work ID, 근거 위치를 한국어 표로 간결하게 보고할 것. 실제 확인하지 않은 상태는 미확인으로 표시하고, 사용자 보고·설계 계획·실제 실행 결과를 구분할 것.
>
> 상태는 개발 / 리뷰(검증 포함) / 인계 / 운영 / 대기 / 완료로 구분할 것. 집중 개발 프로젝트는 최대 3개를 권장하고, 신규 업무 전 기존 Work와 중복 여부를 확인할 것. 배포 성공, 실행 성공, 실제 산출물 생성·검증, 인계 수신·적용을 각각 구분할 것.
>
> 전체 현황 조회만으로 파일을 수정하거나 Job을 실행하지 말 것. 변경·실행·배포·게시 등은 사용자의 명시적 요청과 기존 권한·승인 절차에 따라 처리할 것. 새로운 시스템보다 기존 스킬·Reader·Ledger·Dashboard·Job List를 재사용할 것.
>
> 사용자가 선택한 항목에 대해서는 같은 대화에서 심층 논의를 이어가고, 별도 프로젝트 또는 Work로 분리할 때 Context Handoff를 생성할 것. 최신 결정과 미해결 사항, 원본 링크, 다음 작업을 기록하되 기존 구현 인계서와 혼동하지 말 것.

## 6. 단축 명령 및 표준 응답

| 명령 | 동작 |
|---|---|
| 전체 현황 | 전체 프로젝트 통합 Dashboard |
| 오늘 업무 | 사용자 조치 필요·차단·실패 항목 우선 표시 |
| 진행 현황 | 프로젝트별 최신 상태 및 다음 단계 |
| 스킬 현황 | 활성 버전 / 게시 버전 / 검증 상태 대조 |
| 실행 현황 | Job·Run·Worker·Receipt·Result 대조 |
| 인계 현황 | 최신 인계서 / 수신 / 적용 / 검증 상태 |
| 리뷰 현황 | 리뷰 결과, 자체 검증 및 미해결 판정 |
| 문제점 | 결함·차단 사항·미검증·중복 업무 |
| 주간 정리 | 주요 성과, 남은 업무, 다음 주 우선순위 |
| [항목] 상세 | 관련 원본과 Work를 조회하여 심층 검토 |
| [항목] 맥락 인계 | 개별 프로젝트용 Context Handoff 생성 |

기본 Dashboard 형식:

| 프로젝트 | 상태 | 우선순위 | 최신 확인 사항 | 차단/미확인 | 다음 조치 | 근거/Work ID |
|---|---|---|---|---|---|---|
| 실제 조사 결과 | 실제 판정 | P0/P1/P2 | 확인된 사실 | 미확인 포함 | 권장 조치 | 원본 위치 |

보고 상단에 조회 기준 시각(KST), 접근한 정보 소스, 확인하지 못한 범위를 표시. 근거 없이 전체 프로젝트가 정상이라고 판정하지 말 것. 단순 `DONE/SUCCESS`도 실제 결과의 존재와 동일하지 않음.

## 7. 프로젝트 간 맥락 인계

새 대화나 다른 프로젝트가 기존 대화의 모든 맥락을 자동으로 공유한다고 가정하지 말 것. 프로젝트 기능·메모리·파일 접근 범위는 실제 업무 GPT 환경에서 확인할 것. 공유가 제한되면 기존 Work ID와 원본 링크를 중심으로 다음 Context Handoff를 작성할 것.

```markdown
# [프로젝트명] Context Handoff
- 기준 시각 / Work ID / 최신 리비전
- 이번 논의의 목적
- 확인된 사실과 근거 위치
- 확정된 결정 및 유지 조건
- 미해결 사항 / 미확인 / 차단 사항
- 다음 대화에서 수행할 첫 작업
- 변경·실행 승인 범위
- 관련 원본 및 결과 링크
```

Context Handoff는 GPT 간 논의 재개용이며, 업무 LLM에 구현을 지시하는 정식 Implementation Handoff와 구분. 상세 작업이 끝나면 기존 원본에 결과를 기록하고 Control Center는 그 원본을 다시 조회할 것.

## 8. 모바일 GPT와 업무 GPT의 책임 경계

| 영역 | 모바일 Control Center | 업무 Control Center |
|---|---|---|
| 전체 방향·우선순위 | 종합 판단·협의 | 실제 업무 상태 기반 판단 지원 |
| 기술 설계·인계 | 설계 검토·인계서 관리 | 업무 원본 대조·적용 계획 |
| 실제 소스·스킬 분석 | 허용된 결과 검토 | 업무 환경 원본 관리 및 분석 |
| Job 실행·검증 | 허용된 MCP 결과 조회 | 실제 실행·영수증·결과 관리 |
| 상태 동기화 | 허용된 요약과 링크 확인 | 원본 상태 제공, 승인 범위 준수 |

기존 Job List 및 MCP의 실행·결과 조회 체계는 그대로 활용할 것. MCP를 정식 구현 인계서 전달 채널이나 별도 실행 엔진으로 대체하지 말 것. 모바일 연동은 기존 승인된 읽기 인터페이스의 범위에서만 검토하며 본 인계로 신규 MCP 권한을 부여하지 않음.

## 9. 구축 순서 및 수락 기준

| 단계 | 업무 GPT 수행 내용 | 완료 조건 |
|---|---|---|
| G0 조사 | 프로젝트 기능, 관리 목록, 원본 위치, 접근 권한 확인 | 실제 조사표와 미확인 목록 |
| G1 구조 | 기존 데이터·도구 재사용 방식 및 책임 경계 확정 | 관리 대상·원본·중복 방지 규칙 |
| G2 설정 | 프로젝트 이름, 지침, 참조 원본, 단축 명령 구성안 작성 | 사용자가 적용 가능한 설정 안내 또는 승인된 범위 내 설정 |
| G3 초기 조회 | 전체 현황·오늘 업무·스킬/실행/인계 현황 시험 | 실제 근거 있는 Dashboard 및 조회 시각 |
| G4 맥락 검증 | 대표 항목 상세 조회 후 개별 프로젝트 인계 시나리오 검토 | 재개 가능한 Context Handoff 및 중복 Work 방지 |
| G5 운영 검토 | 모바일/업무 책임 경계와 MCP 조회 가능 범위 점검 | 결과 회신 및 남은 조치 명시 |

필수 수락 조건: 최신 근거 추적 가능, 미확인 표시, 단순 조회의 무변경·무실행, 기존 Work 재사용, 인계/적용 구분, 프로젝트 이동 후 맥락 재개 가능. 현재 제품에 프로젝트 기능이 없다면 기존 GPT 대화와 승인된 공통 관리 문서로 동일한 운영 흐름을 구성하는 대안을 제시할 것.

## 10. 업무 GPT 첫 요청 및 회신

**첫 행동은 G0 읽기 전용 조사.** 기존 업무 프로젝트와 관리 파일, 스킬·Work·Job 상태 소스를 확인하고, 업무 GPT가 실제로 접근 가능한 범위를 정리할 것. 사용자가 직접 설정해야 하는 프로젝트 생성·지침 등록 단계는 구체적인 UI/설정 안내로 분리할 것. 기능 또는 권한이 미확인된 경우 자동 설정 완료로 보고하지 말 것.

다음 항목으로 회신할 것.
- 관리 대상과 기존 원본 위치 / 접근 여부
- 기존 기능 재사용 범위 및 신규 구성 필요 항목
- 최종 프로젝트 지침 및 적용 방법
- 초기 Dashboard 또는 접근 불가 사유
- 프로젝트 간 맥락 인계 방식
- 차단 사항, 승인 필요 조치 및 다음 단계

**현재 인계 범위:** 운영 구조 구축 및 설정 가이드. 기존 스킬 수정, 신규 Job 실행, 자동 배포, 신규 독립 리뷰, 외부 게시, 권한 변경은 포함하지 않음. 실제 설정 변경이 필요하면 기존 승인 절차를 적용할 것.
