5. Shelve와 Push의 결정적 차이: 이력

P4 Shelve

Submit 이력과는 별도

Unshelve해도 shelf 자체는 지워지지 않습니다. shelf는 명시적으로 삭제하거나 다시 shelve해 갱신하기 전까지 남을 수 있습니다. 핵심은 shelf 갱신이 submit된 depot 이력으로 쌓이는 것은 아니라는 점입니다.

Push된 Git Commit

브랜치 이력에 기록

Push된 commit은 해당 branch 이력에 기록됩니다. 리뷰 중 여러 commit을 쌓더라도 팀의 최종 PR 반영은 GitHub에서 Squash and merge로 하나의 반영 단위로 정리합니다.

팀 운영: 담당자가 Build·검증·Review를 완료한 뒤 GitHub 사이트에서 직접 Squash and merge를 수행합니다.

8. “Merge”는 두 방향이 완전히 다르다

이 문서에서 가장 중요한 구분입니다. 같은 “merge”라는 단어를 쓰지만 목적·방향·수행 위치가 다릅니다.

① PR Merge · 최종 반영

내 branch → 공식 branch

GitHub 사이트에서 수행합니다. Build·검증·Review 완료 후 Squash and merge를 클릭하며, P4의 Submit에 가장 가깝습니다.

CL_987654 ── PR ──► smp1900 ↑ GitHub Squash and merge
② git merge · 내 작업 최신화/충돌 재현

base → 내 CL branch

로컬 PC에서 수행합니다. 최신 base를 내 작업 branch에 합쳐 최신화하거나 conflict를 재현합니다. 최종 PR Merge와 다른 동작입니다.

upstream/smp1900 ──► local CL_987654 git merge
원칙: “PR Merge”와 “git merge upstream/smp1900”를 같은 동작으로 읽지 마세요. Part B의 merge는 항상 ②를 뜻하며, 최종 ①은 사용자가 GitHub에서 수행합니다.

9. Git Fetch · Merge · Rebase를 그림으로 이해하기

서버의 최신 상태를 가져오는 것과 그 변경을 현재 branch에 합치는 것은 서로 다른 동작입니다. 8장의 Merge 두 방향 중 여기의 merge는 ② 로컬 merge입니다.

git fetch upstream

서버 상태만 갱신

upstream의 최신 commit 정보를 로컬 repository로 가져옵니다. 현재 작업 파일은 바꾸지 않습니다.

Before upstream/smp1900 → A─B
↓ fetch
After upstream/smp1900 → A─B─C
git merge upstream/smp1900

base를 현재 CL branch에 합침

현재 CL_987654에 최신 smp1900 변경을 합칩니다. 양쪽이 같은 부분을 바꿨다면 conflict가 발생합니다.

Before base A──B──C \ CL └──X After base A──B──C \ \ CL └──X──M M의 부모 = X와 C
git rebase upstream/smp1900

내 commit을 최신 base 위로 다시 쌓음

CL_987654의 commit을 최신 base 뒤에 다시 적용합니다. 기존 commit의 SHA가 바뀝니다.

Before A──B──X base A──B──C rebase 후 A──B──C──X′ X → X′ : 새 SHA
Rebase / force push 주의: 이미 공유된 branch를 rebase하면 commit SHA가 바뀌며, 원격 branch 갱신에 force push가 필요할 수 있습니다. 다른 사람이 사용하는 branch나 자동화가 만든 기존 Open PR branch에서는 기본 동작으로 사용하지 않습니다.
pull은 언제 쓰나? 일상적인 개인 작업에서는 git pull을 사용할 수 있습니다. 다만 Part B의 스킬은 각 단계와 대상 branch를 검증해야 하므로 fetch와 merge를 분리합니다.

10. upstream / local branch 관계

upstream/smp1900처럼 보이는 이름은 “원격 branch의 로컬 사본”이며, 정확한 Git 용어로는 remote-tracking branch입니다. fetch가 이 정보를 갱신합니다.

회사 GitHub 원본 저장소: SMP1900 upstream/smp1900 A──B──C ← base의 remote-tracking branch upstream/CL_987654 A──B──X ← 자동화 PR head의 remote-tracking branch │ │ switch / tracking branch 준비 ▼ local CL_987654 A──B──X ← 실제 파일을 수정하는 local branch ※ fetch만 해서는 작업 파일이 바뀌지 않습니다. ※ local CL_987654로 switch한 뒤 필요한 merge를 수행합니다.
switch

작업 branch 선택

CL_987654를 현재 local branch로 선택해 실제 conflict를 해결합니다.

tracking branch

원격 branch와 연결된 local branch

local CL_987654가 어느 원격 branch를 기준으로 fetch/push할지 연결 관계를 가집니다.

11. Merge와 Rebase 차이

8장의 구분에 따라 여기의 Merge는 base → 내 branch 로컬 통합입니다.

MERGE · Part B 기본 방식

기존 commit을 유지하면서 두 이력을 연결

base A──B──C \ \ CL └──X──M M의 첫 번째 부모 = X M의 두 번째 부모 = C 기존 X는 사라지지 않음

Merge commit M이 X와 C를 모두 부모로 가지므로 기존 CL commit X의 이력을 유지합니다.

VS
REBASE · Part B 기본 사용 안 함

내 commit을 새 base 위에 다시 작성

Before base A──B──C CL A──B──X After base/CL A──B──C──X′ 기존 X → 새로운 X′ SHA 변경

기존 X가 그대로 이동하는 것이 아니라 같은 변경을 기반으로 새 commit X′가 만들어집니다.

다른 저장소에서는 공식 branch를 pilot 또는 main처럼 부를 수 있지만, 이 문서의 base 예시는 smp1900으로 통일합니다.

14. 자동화가 먼저 만든 Open PR에서 시작한다

일반 개발의 Fork 흐름과 달리 이 스킬은 이미 회사 upstream 안에 존재하는 자동화 branch와 Open PR을 이어받습니다.

자동화 시스템이 먼저 수행 P4 SMP1800 CL_987654 ↓ 자동 반영 시도 회사 upstream의 CL_987654 branch 생성 ↓ Open PR 생성 (base = smp1900) ↓ Conflict 발생 ↓ 담당자에게 PR URL + upstream/CL_987654 전달 ↓ ★ 여기부터 l1-cl2git-merge ★
일반 Fork 개발과 구분: 일반 개발은 보통 개인 Fork(origin)에 작업 branch를 push하고 upstream으로 PR을 보냅니다. 반면 이 conflict 복구 스킬은 자동화가 만든 기존 upstream branch 자체를 사용합니다. 자세한 차이는 부록 A를 참조하세요.

15. 정본: l1-cl2git-merge 6단계 흐름

이 문서에서 스킬의 6단계 정의는 이 절 하나만 정본입니다. 다른 절은 이 흐름을 반복하지 않고 여기만 참조합니다.

1로컬 상태 점검현재 repo/branch, 수정 파일, 진행 중 Git 작업, 사용자 변경 보호 여부 확인.
2PR / CL 검증PR=OPEN, head=CL_987654, base=smp1900, 회사 upstream인지 확인하고 CL ID·P4 CL 근거를 확보.
3Fetch + branch 준비upstream 최신 정보 갱신 후 exact CL branch를 local tracking branch로 준비.
4Base Mergeupstream/smp1900을 local CL_987654에 merge.
5CL 의도 보존 확인Conflict가 있으면 해결하고, 없어도 CASE F 누락 검사를 수행한 뒤 정적 검증.
6Commit + Push + PR 확인같은 upstream/CL_987654로 push하고 기존 Open PR 갱신 확인.
STEP 4 Base Merge 완료 ↓ conflict 발생? ├─ YES → conflict 해결 ──────┐ └─ NO ───────────────────────┤ ↓ CASE F: CL 의도 누락 검사 ├─ 누락 있음 → 보완/분석 └─ 누락 없음 ↓ 정적 검증 ↓ STEP 6 Commit + Push ↓ 기존 Open PR 갱신
8장의 Merge 구분을 적용하세요. STEP 4는 “base → 내 CL branch”의 로컬 git merge입니다. 최종 PR Merge는 스킬 범위 밖이며 사용자가 GitHub에서 수행합니다.
왜 pull 대신 fetch + merge인가? 일상 작업에서는 pull을 사용할 수 있지만, 이 스킬은 PR·remote·branch와 각 단계 결과를 검증해야 하므로 fetch와 merge를 분리합니다.

17. 상황별로 스킬은 어떻게 행동하나?

CASE A

로컬에 수정 중인 파일이 있음

사용자 작업을 삭제하지 않습니다. 안전하게 보존할 수 있으면 스킬의 안전한 보존 방식으로 보호하고, 불가능하면 사용자에게 확인 후 중단합니다.

금지: 임의의 reset --hard, clean -fd
CASE B

같은 local CL branch가 이미 있음

로컬에만 있는 commit이 있는지 먼저 확인합니다. 고유한 미Push commit이 있으면 강제로 지우거나 덮어쓰지 않습니다.

안전할 때만 오래된 local branch를 정리
CASE C

PR / branch 정보가 맞지 않음

PR이 OPEN이 아니거나 base/head/upstream 조건이 다르면 진행하지 않습니다.

BLOCKED: 임의로 새 branch나 새 PR을 만들어 우회하지 않음
CASE D

단순 Conflict

라인 이동, include 위치 변경, 명확한 rename/move처럼 CL 의도가 분명한 경우 동일 branch에서 해결합니다.

분류: SAFE_CONFLICT
CASE E

20. 용어집

remote-tracking branch
upstream/smp1900처럼 원격 branch의 상태를 로컬 repository 안에서 가리키는 참조. fetch로 갱신됩니다.
tracking branch
특정 원격 branch와 연결 관계가 설정된 local branch. 예: local CL_987654가 upstream/CL_987654를 추적.
head / base
PR에서 head는 변경을 가져오는 작업 branch, base는 변경을 넣으려는 대상 branch입니다.
SHA
Git commit을 식별하는 해시 값. rebase처럼 commit을 다시 작성하면 SHA도 달라집니다.
force push
원격 branch 이력을 일반적인 fast-forward 규칙을 무시하고 갱신하는 push 방식. 공유 branch에서는 이력 충돌 위험이 있어 주의가 필요합니다.
부록 A

Fork · Clone · origin · upstream

일반 개발의 Fork 모델과 l1-cl2git-merge의 예외적 upstream 직접 작업을 분리해서 봅니다.

A-1. 일반 개발: SMP1900을 Fork해서 사용

팀의 일반 개발 흐름에서는 회사 원본 repository인 SMP1900을 개인 계정으로 Fork해 사용합니다. l1-github fork-setup 기준 역할은 아래와 같습니다.

upstream

회사 원본 / canonical repository

base 시작 기준, 최신 base 가져오기, PR target 역할입니다.

upstream ↓ 회사 SMP1900
VS
origin

내 Fork

일반 feature/fix branch를 push하는 개인 작업 repository입니다.

origin ↓ 내 Fork of SMP1900
[회사 GitHub] upstream = SMP1900 │ │ Fork ▼ [내 GitHub] origin = 내 SMP1900 Fork │ │ clone / feature 작업 / push ▼ [내 PC] local feature branch │ └──── PR ────► upstream/smp1900
remote 이름은 Git이 강제하는 고정어가 아닙니다. 다만 팀의 l1-github fork-setup은 upstream = 회사 원본, origin = 개인 Fork 역할로 구성합니다.

A-2. l1-cl2git-merge는 일반 Fork 작업과 다르다

자동화 conflict 복구에서는 이미 회사 upstream repository 안에 CL_987654 branch와 Open PR이 존재합니다. 따라서 개인 Fork에 새 branch를 만들지 않습니다.

[회사 upstream SMP1900] upstream/smp1900 │ └── 자동화 생성 ──► upstream/CL_987654 │ ├─ 기존 Open PR │ └─ 담당자가 같은 branch 이어받음 ↓ conflict 해결 / commit ↓ upstream/CL_987654 push ↓ 기존 Open PR 갱신 ※ 새 개인 Fork branch / 새 PR을 만들지 않음
Part B 전제: l1-cl2git-merge는 Git remote 처리 로직을 자체 복제하지 않고 l1-github에 맡깁니다. supplied PR은 remote=upstream, base=smp1900, head=CL_987654 조건을 만족해야 합니다.
