## 2. 코드 폴더 사전 확인

**분석 대상은 업무 호스트의 제품 소스 폴더예요.** 업무 GPT가 다음 분기를 설계하고, 실행 호스트의 Qwen 또는 허용된 로컬 Agent가 읽기 전용으로 확인해요. GitHub 인계 문서의 위치, 스킬 설치 폴더, 결과를 저장하는 Workspace는 각각 용도가 달라요.

| 실행 때 확인한 상황 | 동작 |
|---|---|
| 이번 요청에 제품 소스 경로가 있음 | 지정 경로의 존재·읽기 권한·대상 프로젝트를 먼저 확인해요. 읽을 수 없거나 프로젝트가 다르면 이유와 함께 올바른 경로를 한 번 물어요. 저장된 다른 경로로 자동 전환하지 않아요. 경로·프로젝트가 유효하면 아래 revision 분기로 이어가요. |
| 경로 미지정, 같은 호스트·프로젝트에 유효한 저장 경로가 하나 있음 | 저장 경로를 검증하고 **경로 재질문 없이 재사용**해요. 아래 revision 분기로 이어가요. |
| 경로 기록 없음, 이동·권한 문제, 다른 저장소, 복수의 유효 후보 | 확인 가능한 원인이나 후보만 제시하고 **“이번에 분석할 제품 소스 폴더 경로가 어디인가요?”**라고 한 번 물어요. 여러 후보면 확인된 경로 중 하나를 고를 수 있게 해요. |
| 경로·프로젝트 유효, 요청 revision과 관찰 revision 일치 | 기존 조회 범위와 지정 revision을 고정하고 질문 없이 분석해요. |
| 경로·프로젝트 유효, 요청 revision과 관찰 revision 불일치 | 두 revision과 불일치 이유를 제시하고 **“이번 분석에 어느 revision을 사용할까요?”**라고 한 번 물어요. 현재 경로 재입력을 요구하지 않아요. 사용자가 선택한 revision을 해당 호스트에서 읽을 수 있는지 확인한 뒤 고정해요. |
| 유효한 경로, 요청 revision 미지정 | 이번 실행에서 관찰한 Git branch/commit 또는 P4 stream·파일 revision을 고정해요. 같은 경로에서 HEAD가 바뀌면 질문 없이 새 revision의 영향을 받는 기존 근거를 갱신해요. |
| 사용자가 답함 | 경로 또는 선택 revision을 검증해요. 둘 다 유효할 때 분석을 시작하고 허용된 기존 기록에 저장해요. 이번 요청 전용 값은 그 범위에만 기록해요. 응답이 유효하지 않거나 아직 해결되지 않은 조건이 있으면 구체적 사유와 확인 대기·재개 위치를 남겨요. 사용자가 값을 바로잡으면 필요한 분기에서 재개해요. |
| 응답을 받을 수 없는 무인 실행 | 확인할 경로/revision, 필요한 선택과 이유를 기존 Work에 남겨요. 확보한 Seed 정보는 보존하고 입력 검증 뒤에 분석을 재개해요. |

Git이면 요청한 디렉터리와 실제 저장소 루트·상대 범위, 현재 branch 또는 고정 commit을 대조해요. P4이면 기존에 허용된 client/view의 로컬 매핑과 대상 stream/depot 범위를 확인해요. Git 메타데이터가 없는 정식 소스 스냅샷은 기존 릴리스 식별 근거를 사용해요. 경로·프로젝트 확인 후 지정 revision의 일치 여부를 별도로 확인해요. 경로와 revision을 함께 확인해야 하는 경우 현재 알 수 있는 선택 조건을 한 번의 질문에 묶어요. 최초 입력 확인에서 사용자 질문은 최대 1회예요. 답변 뒤에도 입력 고정이 안 되면 질문을 반복하지 않고 대기 상태와 재개 위치를 기록해요. 입력 고정이 완료되기 전에는 제품 소스 분석을 시작하지 않아요. 임의의 현재 디렉터리 선택·디스크 전체 탐색·자동 checkout은 하지 않아요. 실제 경로와 고정 revision은 업무 Work에 보존해요.

## 3. 현행 스킬을 Qwen 구현 지침으로 바꾸는 순서

업무 GPT는 기존 스킬 원문·지원 action·기존 Work 표본을 대조해, 단계마다 **현재 담당 기능 / 확인한 입력과 출력 / 변경이 필요한 지점 / 통과할 시험**을 적어요. 로컬 Agent가 확인할 수 없는 설치 정보는 미확인으로 남겨요. 아래 V0~V6는 분석 순서이고, 설치본에 적용할 함수명과 인자명은 업무 GPT가 실제 계약에서 찾아요.

| 단계 | Qwen이 맡을 한 단위 | 다음 단계로 넘길 근거 |
|---|---|---|
| V0 · 입력 고정 | 기존 Work·영수증을 확인하고 2절의 코드 폴더, Seed CL/PR, 현재 대상 revision·빌드 옵션을 고정 | 재사용할 결과, 이번 조회 범위, 미확인 항목 |
| V1 · Seed 전후 | Git은 실제 landing과 부모, P4는 변경 파일별 전후 revision을 대조. Jira·PR 주장과 코드·시험 사실을 구분 | 증상, 발생 전제, 원인, Fix 효과 및 적용 한계. 복수 원인은 분리 |
| V2 · 원인 규칙 | 대상 객체·세대·소유권, 실패 가능 조건, 지켜야 할 순서, 위반 결과, 필요한 보호를 한 문장으로 작성 | 수정 전·후와 안전한 유사 사례로 보정한 규칙. 설명되지 않는 전제는 보류 |
| V3 · 현재 후보 | 같은 API·상태·자원·소유 경계의 사용처부터 찾고 한 번에 한 조건만 확장 | 검색 범위·매치·중복 제거 후보·제외·미조사. 검색 실패·잘림은 별도 기록 |
| V4 · 보호 판정 | 후보 하나의 빌드 활성·분기·반환·상위/하위 보호·공유 자원·정상 반례를 대조 | 실행 가능한 경로, 첫 위반 시점, 보호의 적용 범위, 판정과 반대 근거 |
| V5 · 조치 선택 | 원인 수정·사전 검사·관측 보강·국소 복구·상위 이관을 현재 후보에서 비교 | 우선 조치, 적용/금지 조건, 소유자, 정리·종료·복귀 확인, 실패 시 처리 |
| V6 · 보존·검증 | 확인된 시나리오를 변환하고 같은 Work에서 결과를 재조회. 분석 품질과 제품 효과를 각각 시험 | 두 스킬 호출 근거, 보고서·MSC·Viewer 결과, 미검증 범위와 다음 한 행동 |

Seed 위치에 Fix가 들어간 경우에도 다른 후보의 조사는 계속해요. 원 수정을 같은 위치에서 빠뜨린 경우와 다른 경로의 변형을 구별해요. 신규 후보와 원래 Jira의 관계는 ‘같은 원인 규칙의 근거’로 기록해요.

### Qwen에 한 번에 주는 질문과 회수할 답

| 입력에 넣을 것 | 답에서 확인할 것 |
|---|---|
| 원인 규칙 하나, 대상 revision·빌드, 후보 함수의 관련 분기·return·정리, caller/callee 또는 wrapper의 보호 근거, 정상 반례 하나 | “같은 작업의 첫 잘못된 통지나 상태 사용 전에 이 보호가 효력을 내는가?”에 대한 판정, 지지·반대 근거 위치, 결정적인 미확인 경계 하나 |
| callback·IPC·간접 호출이 있으면 등록부와 전달부, 객체·세대 또는 Stack/domain/CC를 잇는 근거 | 같은 작업이라는 근거와 순서 보장 수단. 순서가 열려 있으면 필요한 등록부·호출부·기존 trace 중 다음 조회 하나 |
| 실제 조회한 범위와 남은 후보, 사용 가능한 시간·입력 예산 | 추가 조회로 새 근거가 생기면 해당 후보를 보강. 예산 소진·추가 근거 없음이면 확인 범위와 잔여 후보를 저장하고 재개 위치 기록 |

판정은 **이미 해결됨 / 발생 불가능 / 미해결 확인 / 추가 검증 필요** 중 하나를 사용해요. ‘이미 해결됨’에는 적시에 작동하는 동등 보호, ‘발생 불가능’에는 현재 빌드나 객체의 전제 불성립 근거가 필요해요. ‘미해결 확인’에는 같은 작업에서 입력→분기→위반이 이어지고 관련 보호가 위반을 막지 못하는 근거가 필요해요. 코드로 확인한 범위와 제품에서 관찰한 범위를 표시해요. 조사하지 않은 후보는 별도 집계해요.

## 4. 놓치는 사례에서 해결안을 고르는 기준

**합성 C++ 사례의 판정을 가른 것은 상위 통지 시점이었어요.** 두 실패 경로 모두 RF 자원을 반납했어요. 한 경로는 HAL 실패를 확인하고 실패를 한 번 통지했고, 다른 경로는 HAL 호출 후 결과를 분기하기 전에 성공을 한 번 통지했어요. 두 번째 경로에서는 자원이 정리돼도 상위는 성공으로 진행할 수 있어요. 아래 조치는 업무 GPT가 실제 계약에 맞춰 채택할 설계 후보예요.

| 후보에서 확인한 조건 | 해결 방향 | 수락할 증거 |
|---|---|---|
| HAL의 동기 실패 반환이 있고 성공 통지 시점을 옮길 수 있음 | 반환을 판정한 뒤 성공/실패로 분기. 성공은 정상 완료를 한 번 통지. 실패는 해당 작업의 소유자가 획득분만 정리하고 실패를 한 번 통지 | 성공·실패 양쪽에서 최종 통지 종류·횟수, 자원 상태, 상위의 최종 상태를 함께 관찰 |
| 비동기 요청 접수와 실제 완료가 분리됨 | API가 의미하는 접수·완료를 먼저 정의. 최종 성공은 같은 작업의 완료 근거 뒤에 확정하고, 지연·중복·이전 세대 응답을 기존 식별 규칙으로 처리 | 정상 지연에서 오판 없음. 이전 작업의 완료가 새 작업으로 귀속되지 않음 |
| 이미 최종 성공이 전달돼 상위 상태가 바뀜 | 잘못된 통지를 예방하는 수정을 우선. 이미 전이한 작업은 상위 소유자와 기존 취소·상태 재동기화 계약을 조사. 안전한 정정 수단이 없으면 상위 이관 또는 국소 복구 보류 | 실패 통지를 무조건 덧붙여 이중 종료하지 않음. 상·하위 상태 일치와 다음 정상 요청이 가능한지 확인 |
| 정적 위반은 보이지만 런타임에서 실패와 정상 중간 상태를 구별할 신호가 없음 | 부작용 전 검사·원인 수정을 우선. 필요한 관측값·시점·소유자를 지정하고, 신뢰할 판별 근거가 생길 때까지 자동 복구 보류 | 정상 반례를 오인하지 않고 관측값이 확보될 때 오류를 구분. 근거가 없으면 무엇을 관측해야 하는지 명시 |
| 실패 신호는 있으나 부분 HW 반영·공유 RF·타 Stack 영향 또는 소유권이 불명확 | 부분 적용 범위와 소유권 이전을 추적. 권한 있는 기존 소유자에게 전달하고 국소 정리·재시도의 안전 범위 결정 | 실제 획득분만 한 번 정리. 중복·release·경쟁, 복구 자체 실패, 다른 Stack 및 다음 요청 확인 |
| 분석기가 다른 함수를 진입점으로 골랐거나 MSC 순서가 코드와 다름 | 대상 함수의 분기·반환과 caller/callee 근거를 다시 확인. Recovery가 검증한 순서로 시나리오 입력을 고친 뒤 필요한 변환만 재실행 | 선택한 진입점·코드 위치·조건이 일치. 근거 없는 비동기 순서는 미확인. 순서를 뒤집은 대조 입력 검출 |

국소 복구를 제안할 때는 **검출 신호 → 정리 권한 → 부분 부작용 → 종료 통지 → SW/HW 복귀 확인 → 복귀 실패 시 이관**을 한 경로로 설명해요. 제품 변경으로 이어질 때는 기존 실시간 요구와 고정 자원 규칙(`new/delete` 금지)을 적용해요.

## 5. 두 필수 스킬과 Work·Viewer 연결

1. **`code-analyzer` 실제 호출.** Recovery가 고정된 소스와 대상 심볼로 기존 action을 호출해요. 생산자 버전·action·입력 revision/범위·실제 결과·실패 상태·파일/함수/분기 근거를 기록해요. 평가에 사용한 `v0.15.5` 개발 후보는 합성 함수 6개를 찾았지만 `--focus latePath`를 주어도 기본 진입점이 `releaseRf`였어요. 요약이 비어 있으면 함수별 사실과 실제 소스를 대조하고, 핵심 경계를 찾지 못하면 판정을 보류해요.
2. **MSC 입력 검증.** Recovery가 Seed 수정 전·후, 현재 후보 AS-IS, 제안 조치 TO-BE를 구분해요. AS-IS의 발신·수신·순서·분기는 각각 원본 revision과 근거에 연결해요. 비동기 순서는 이벤트 대응 근거가 필요해요. Edge의 의미·생성 조건·근거 표시는 업무 GPT가 기존 Recovery 계약에서 확정해요. 정의가 미확정이면 Edge 자체와 Edge에 의존하는 출력 요소를 미확정으로 표시하고, 해당 요소의 의미나 연결을 추정하지 않아요. 노드·발신/수신·순서 등 Edge와 무관하고 근거가 검증된 MSC 요소는 생성·변환을 진행해요. Edge 때문에 전체 시나리오를 올바르게 표현할 수 없는 부분은 해당 부분의 보류와 이유를 남겨요. TO-BE에는 제안임을 표시하고 조치가 없으면 해당 없음과 이유를 남겨요.
3. **`doc-converter` 실제 호출.** 검증한 시나리오 입력과 지원 action으로 변환하고 버전·입력 해시·결과/영수증을 남겨요. 합성 시험에서 `v0.2.26`은 순서를 뒤집은 입력도 형식 검증을 통과시켰어요. 변환 전 의미 검증과 변환 후 결과 대조가 모두 필요해요. 원본 PlantUML·SVG·B형 HTML 각각의 생성 여부와 상대 링크·해시를 기록해요. 변환 후 순서·방향·메시지 대응과 근거를 대조해 불일치하거나 검증할 수 없음이 확인되면 해당 미검증 MSC의 등록·링크·완료 판정을 차단해요. 실패 근거와 원본 입력은 같은 Work에서 보존하고 4절의 시나리오 입력 검증으로 돌아가 필요한 변환만 다시 실행해요. 이미 검증된 다른 산출물과 코드 분석 근거는 재사용해요.
4. **같은 Work에서 보존·열람.** 기존 Work/Evidence writer의 preview→원본 SHA·Evidence revision 고정→등록→재조회를 사용해요. 11월 24일 개발 계약은 `provider=l1-channel-recovery`, `kind=recovery_analysis`, `stage=utility`이며 설치본과 먼저 대조해요. 기존 `RECOVERY.md`·`index/recovery.json` 및 `recovery/`는 원본을 가리키는 파생 보기예요. Viewer의 Recovery 목록→사례→같은 Work→HTML/SVG 실제 열람까지 단계별로 확인해요.
5. **부분 실패와 재개.** 새 분석의 완료에는 두 생산자의 실제 호출 근거가 필요해요. 변환할 사실이 없으면 미확인 단계와 이유를 보존해요. 입력·버전·revision이 일치하는 기존 실행은 영수증을 재사용해요. 렌더러가 없으면 코드 판정·입력·생성된 PUML은 보존하고 렌더부터, 저장 충돌은 최신 Work 재조회와 등록부터, 링크 누락은 연결부터 이어가요. 변환 후 의미 대조 실패는 시나리오 입력 보정·재검증부터, 필요한 변환만 이어가요. 의미 검증을 통과한 결과 파일만 산출물로 등록·링크하고 실패한 MSC를 포함한 단계는 보류로 표시해요.

11월 24일 인계의 Viewer `v0.5.3`과 Kernel `v0.7.47`은 개발 전달본이에요. Workflow `v1.6.75`에는 ZIP 내용이 다른 기존 후보가 둘이어서 설치본의 실제 소스·해시·지원 경로로 매핑해요. 실행에 필요한 활성 설치본의 매핑을 확인할 수 없으면 해당 Workflow에 의존하는 Recovery 실행을 보류하고, 확인하지 못한 항목·담당·재개 조건을 기존 Work에 남겨요. 확인 가능한 설계 검토와 이미 확보한 근거는 보존해요. 매핑이 확인된 뒤에 입증된 호환성 결손만 보완하고 검증을 이어가요. 코드 폴더·Work·권한 정보는 허용된 업무 호스트에서 확인하고, 외부 인계 저장소는 업무 스킬의 실행 의존성에 넣지 않아요.

## 6. 첫 수락 시험과 업무 GPT 회신

아래는 **업무 환경에서 수행할 시험 계획**이에요. 11월 25일 평가에서 직접 실행한 범위는 합성 C++ 성공·실패 4조합, Analyzer 함수·호출 근거 조회, Converter 형식 검증과 PUML 생성까지예요. 평가에서는 Analyzer의 호출 위치를 합성 소스와 대조해 Converter의 시나리오 입력을 별도로 작성했어요. PlantUML 렌더러가 없어 SVG·HTML은 생성되지 않았어요. 업무 Qwen 성능, 자동 연동, 제품 복구 효과는 아직 미검증이에요.

| 확인할 동작 | 시험 입력과 기대 결과 |
|---|---|
| 코드 폴더 선택 | 이번 지정 경로가 유효하면 저장값보다 우선. 경로 무효·프로젝트 불일치면 유효한 저장값이 있어도 경로 질문 1회, 응답 전 제품 소스 분석 0회. 지정이 없고 저장값이 유효하면 경로 질문 0회. 미설정·이동·권한 문제·복수 후보에서는 필요한 경로 확인 1회. |
| Revision 선택 · M1 | 명시 경로 또는 저장 경로는 유효하고 요청 revision과 관찰 HEAD만 다름 → 두 revision을 제시하고 revision 선택 질문 1회, 경로 재질문 0회, 고정 전 제품 분석 0회. 승인된 선택을 읽을 수 있으면 고정·기록. revision 미지정인 같은 경로의 HEAD 변경 → 질문 0회, 새 revision 기록 및 영향 근거 갱신. 응답으로도 해결되지 않거나 무인 상태면 대기·재개 지점 보존. 같은 유효 입력으로 재개하면 재질문 0회. |
| 후보 판정·범위 | 보정용 비-timeout Seed와 별도 평가 사례를 준비하고 C++ 담당자가 예상 판정을 먼저 고정. 알려진 미해결 후보, 상위 보호, 늦은 정리, 비활성 빌드, 불명확한 callback을 대조. 조사·미조사·보류 수와 분모를 함께 보고 |
| 검출 및 조치 | 4절의 성공/실패·기존 성공 통지·중복/지연·다른 소유자 사례에서 신호·통지 횟수·자원·상위 상태·다음 정상 요청을 검증. 자동 복구를 보류할 사례도 정답에 포함 |
| 분석·변환·보존 | 진입점 불일치, 뒤집힌 MSC 순서, 미확인 메시지, 렌더러 누락, Work 저장 충돌, Viewer 링크 누락을 각각 대조. 두 호출 영수증과 실제 산출물을 확인하고 실패한 단계에서 재개 |
| 변환 후 의미 검증 · N1 | Converter 형식 검증은 PASS이나 의미 대조에서 역순·방향 불일치 검출 → 문제 MSC 등록·링크 0건, Work에 실패 근거·입력 보존, 시나리오 재검증 및 해당 변환 재개. 보정본의 의미 검증 및 실제 파일 재조회 PASS일 때만 등록·링크. |
| 활성 Workflow 매핑 · N2 | 같은 v1.6.75 후보가 복수이고 실제 설치본 해시/지원 action을 확인할 수 없음 → 의존 실행 보류, 원인과 재개 조건 기록. 매핑 확인 후에 기존 계약을 검증해 재개. |
| Edge 미확정 · N3 | Edge 정의가 없는 검증된 시나리오 → Edge와 의존 요소는 미확정 표시, 독립적으로 검증된 노드·메시지·발신/수신·순서 등은 MSC 생성·변환. 미확정 부분을 사실처럼 렌더링하지 않음. 출력 의미 대조와 미확정 표기 확인. |
| Qwen 절차 비교 | 기존 방식과 새 방식을 같은 모델 설정·코드·빌드·사례·시간/토큰 예산에서 비교. 알려진 결함 누락·정상 오탐·근거 없는 확정·잘못된 MSC 순서·보류율·처리 비용을 기록. 첫 권장 수락 기준은 알려진 미해결 경로 식별, 대조 사례 기대 판정 일치, **근거 없는 확정과 잘못된 MSC 순서 각 0건** |

업무 GPT가 먼저 회신할 결과는 **기존 구현과의 차이, Qwen에 줄 변경 지침, 첫 시험의 입력과 예상 판정**이에요. 실제 실행 뒤에는 Work ID·대상 revision, 코드 경로 확인 결과, 후보별 근거·조치, 두 스킬 영수증, 산출물 재조회와 Viewer 열람, 시험별 PASS/FAIL/SKIP/NOT_RUN 및 다음 한 행동을 같은 Work에 기록해요. 업무 소스·로그·상세 MSC는 허용된 업무 Work에 보존해요.
