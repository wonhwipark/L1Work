00

시작 전에

터미널을 열고, 딱 두 줄만 설정하고, 규칙 하나를 정합니다.

터미널 열기

Ctrl + ` (백틱, 숫자 1 왼쪽). VS Code 아래쪽에 터미널이 열립니다. 오른쪽 위에 powershell 또는 pwsh라고 떠 있으면 맞습니다.

최초 1회 설정

PowerShell
PS> git config --global core.autocrlf true PS> git config --global core.quotepath false PS> git config --global user.name "본인 이름" PS> git config --global user.email "wh1112.park@samsung.com"

autocrlf는 Windows 줄바꿈(CRLF)을 저장소에는 LF로 넣어 줍니다. 빼면 파일 전체가 바뀐 것처럼 보입니다. quotepath false는 한글 파일명이 \355\225\234처럼 깨져 보이는 것을 막습니다.

C++ 코드 포맷(clang-format) 설정은 09절에 따로 있습니다. git을 먼저 익히고 나중에 하셔도 됩니다.

규칙 하나

왼쪽 Source Control 패널은 보는 용도로만 씁니다. 조작은 터미널에서 합니다.

특히 Sync Changes 버튼을 누르지 마세요. pull과 push를 한꺼번에 하기 때문에 의도하지 않은 merge commit이 생기고, 지금 무슨 일이 벌어졌는지 알 수 없게 됩니다. 익숙해진 뒤에 다시 쓰면 됩니다.

01

저장소가 3개다

P4는 서버 하나였습니다. Git Fork 방식은 셋입니다. 헷갈리는 거의 모든 문제가 "지금 어느 저장소를 건드리고 있는가"를 놓쳐서 생깁니다.

내 PC 작업 폴더

파일을 실제로 고치는 곳. 여기서 한 일은 아직 아무도 못 봅니다.

commit해도 여기까지
내 Fork origin

서버에 있는 내 전용 복사본. 마음대로 push해도 팀에 영향이 없습니다.

push 대상 · 항상 여기
정식 저장소 upstream

팀 공용. 여기로는 직접 push하지 않습니다. PR로만 들어갑니다.

읽기 · branch 기준 · PR 대상

이름이 헷갈릴 수 있는데, origin이 정식 저장소가 아닙니다. Fork를 clone했기 때문에 origin은 내 Fork를 가리킵니다. 정식은 별도로 upstream이라는 이름을 붙여 씁니다.

하고 싶은 일어디를 건드리나
새 branch 만들기기준은 upstream, 만들어지는 곳은 내 PC

02

최초 1회 설정

저장소를 처음 받을 때 한 번만 합니다. 이미 폴더가 있으면 remote 확인만 하세요.

먼저 GitHub 웹에서 정식 저장소로 가서 오른쪽 위 Fork를 누릅니다. 내 계정 밑에 복사본이 생깁니다. 그다음 내 Fork 주소를 clone합니다.

PowerShell
PS> cd D:\workspace PS> git clone https://slsi.github.samsungds.net/wh1112.park/smp1900.git # ← 본인 계정 PS> cd smp1900
origin 내 Fork를 내 PC로 복사

이 시점에 origin은 자동으로 등록됩니다. 정식 저장소는 직접 붙여야 합니다.

PowerShell
PS> git remote add upstream https://slsi.github.samsungds.net/cpswdev-team/smp1900.git PS> git remote -v origin .../wh1112.park/smp1900.git (fetch) origin .../wh1112.park/smp1900.git (push) upstream .../cpswdev-team/smp1900.git (fetch) upstream .../cpswdev-team/smp1900.git (push)
upstream 정식 저장소를 이름으로 등록 (아직 통신 안 함)
줄이 4개인 이유

remote는 origin과 upstream 2개입니다. git은 "받아올 때 쓸 주소"와 "보낼 때 쓸 주소"를 따로 가질 수 있어서 (fetch) / (push)로 나눠 보여줄 뿐입니다. 보통은 두 줄이 같은 주소이고, 다르게 쓸 일은 거의 없습니다.

upstream ... (push)가 보여도 정식 저장소에 push할 수 있다는 뜻이 아닙니다. "만약 push한다면 이 주소를 쓴다"는 설정값일 뿐이고, 실제로 막는 것은 서버 권한입니다. git 설정에는 어디로 갈지만 있고, 되는지는 서버가 정합니다.

확인

git remote -v에서 origin은 내 계정, upstream은 팀 계정이면 맞습니다. 둘 다 팀 계정이면 Fork가 아니라 정식을 clone한 것입니다. 이 상태로 진행하면 push가 거부됩니다.

03

매일 쓰는 5단계

작업 하나를 시작해서 PR 직전까지. 이 다섯 개가 전부입니다.

  1. 정식 최신 상태를 받고, 거기서 branch를 판다

    branch 기준은 항상 upstream입니다. 내 Fork는 뒤처져 있을 수 있습니다.

    PowerShell
    PS> git fetch upstream PS> git switch -c feature/ABC-123-tx-fix upstream/dev Switched to a new branch 'feature/ABC-123-tx-fix'
    upstream 최신 상태를 읽어와서 내 PC 에 branch 생성
    VS Code 좌하단 상태바의 branch 이름이 feature/ABC-123-tx-fix로 바뀝니다. 이게 지금 내가 서 있는 자리입니다.
  2. 코드를 고치고, 올릴 파일을 고른다

    P4에 없던 단계입니다. 고친 파일 중 이번 commit에 넣을 것만 따로 지정합니다.

    PowerShell
    PS> git status modified: src/TxSwitchMngr.cpp modified: debug_temp.log PS> git add src/TxSwitchMngr.cpp
    내 PC 아직 아무 데도 안 나갑니다
    VS Code Source Control 패널에서 TxSwitchMngr.cpp가 Changes에서 Staged Changes로 이동합니다. debug_temp.log는 Changes에 그대로 남습니다 — 이게 "고른다"의 의미입니다. 눈으로 한 번 보면 개념이 잡힙니다.

    파일이 여러 폴더에 흩어져 있을 때

    아래 상태를 기준으로 각 명령이 무엇을 담는지 비교한 것입니다.

    git status
    M doc/note.md M src/rx/RxCfg.cpp M src/tx/TxSwitchMngr.cpp ?? src/tx/TxNew.cpp ← 새로 만든 파일 ?? build/ ← 빌드 산출물
    명령담기는 것
    git add src/tx/A.cpp src/rx/B.cpp 나열한 파일만. 가장 안전합니다. 경로는 띄어쓰기로 이어 씁니다.
    git add src/ src 아래 전부. 새 파일 TxNew.cpp도 들어갑니다.
    git add -u 이미 추적 중인 파일의 수정만. TxNew.cpp와 build/는 제외됩니다.
    git add "*.cpp" 저장소 전체의 .cpp 전부. doc/note.md는 빠집니다.
    git add -A 저장소 전체 전부. build/까지 딸려옵니다.

    실제로는 git add -u를 가장 많이 쓰게 됩니다. "고친 것만 올리고 새로 생긴 잡파일은 건드리지 마"라는 뜻이라 실수가 적습니다.

    git add . 의 함정

    git add .은 지금 서 있는 폴더 아래만 담습니다. src/tx에서 치면 src/rx와 doc은 들어가지 않습니다.

    git status 출력에 ../rx/RxCfg.cpp처럼 ../가 보이기 시작하면 저장소 루트가 아니라는 신호입니다.

    VS Code 사실 가장 편한 방법입니다. Source Control 패널에서 파일 이름 위에 마우스를 올리면 + 버튼이 뜹니다. 폴더가 나뉘어 있어도 목록은 한 곳에 모여 있어서 눈으로 보며 고를 수 있고, 동작은 git add와 완전히 같습니다.
  3. commit — 내 PC에 기록

    commit은 제출이 아닙니다. 아직 내 PC 밖으로 한 발자국도 안 나갔습니다.

    PowerShell
    PS> git commit -m "ABC-123 TxSwitchMngr null check 추가" [feature/ABC-123-tx-fix 0501410] ABC-123 TxSwitchMngr null check 추가
    내 PC 기록 완료 · 서버는 아직 모름
    VS Code Staged Changes가 비워지고, 좌하단 branch 이름 옆에 ↑1이 생깁니다. "서버에 안 보낸 commit 1개"라는 뜻입니다.
    -m 은 message

    안 붙이면 편집기가 열려서 메시지를 쓰라고 합니다. 까만 화면에 vim이 열렸다면 Esc → :wq → Enter로 빠져나오세요.

  4. push — 내 Fork로 보낸다

    처음 한 번만 -u origin <branch>를 붙입니다. 그다음부터는 git push만으로 됩니다.

    PowerShell
    PS> git push -u origin feature/ABC-123-tx-fix ... * [new branch] feature/ABC-123-tx-fix -> feature/ABC-123-tx-fix
    내 PC → origin commit된 것만 갑니다
    VS Code 좌하단 ↑1이 사라집니다. 아직 ↑가 남아 있으면 안 올라간 commit이 있는 겁니다.
    -u 는 짝 등록

    --set-upstream의 줄임입니다. "이 branch는 앞으로 origin의 이 branch와 짝"이라고 등록합니다. 한 번 해두면 그다음부터는 git push만으로 됩니다. 좌하단 ↑1 표시도 이 짝이 있어야 나옵니다 — 짝이 없으면 몇 개나 안 올렸는지 셀 기준이 없습니다.

    같은 -u인데 뜻이 다릅니다. git add -u는 --update(추적 중인 파일만), git push -u는 --set-upstream(짝 등록)입니다. 명령마다 옵션 글자가 따로 정해져 있어서 그렇습니다. 헷갈리면 긴 이름으로 쓰셔도 됩니다.

  5. PR — 정식 저장소로 요청

    여기부터는 웹입니다. GitHub에서 내 Fork로 가면 방금 push한 branch에 대해 Compare & pull request 버튼이 떠 있습니다.

    origin → upstream base가 dev인지 반드시 확인
    확인

    PR 화면 위쪽이 cpswdev-team/smp1900 : dev ← wh1112.park/smp1900 : feature/... 형태여야 합니다. 왼쪽(base)이 내 계정으로 되어 있으면 내 Fork 안에서만 도는 PR입니다.

04

정식이 앞서갔을 때

리뷰 도중 다른 사람 코드가 먼저 merge되는 상황. Fork 방식에서 가장 자주 하게 될 작업입니다.

PowerShell
PS> git fetch upstream e4483cb..2463939 dev -> upstream/dev PS> git merge upstream/dev Merge made by the 'ort' strategy. PS> git push
upstream → 내 PC → origin

왜 git pull이 아닌가. pull은 fetch와 merge를 한 번에 합니다. 편하지만 초보자에게는 "무엇을 가져왔는지" 볼 기회가 사라집니다. 나눠서 하면 fetch 출력에서 정식이 얼마나 앞서갔는지 먼저 확인하고 merge할 수 있습니다. 그리고 pull은 기본적으로 origin(내 Fork)을 봅니다 — 여기서 원하는 건 upstream입니다.

먼저 확인하고 싶다면

git log --oneline HEAD..upstream/dev — 정식에는 있고 내게는 없는 commit 목록.

git log --oneline -10 — 최근 10개. 화면 아래에 :만 뜨고 멈추면 q를 누르세요. 고장난 게 아니라 페이지 넘김 모드입니다.

05

충돌(conflict)

같은 줄을 나와 다른 사람이 동시에 고쳤을 때. 겁먹을 일이 아니라 그냥 손으로 고르는 작업입니다.

PowerShell
PS> git merge upstream/dev CONFLICT (content): Merge conflict in src/TxSwitchMngr.cpp Automatic merge failed; fix conflicts and then commit the result.

파일을 열면 이렇게 되어 있습니다.

src/TxSwitchMngr.cpp
if (pCtx == nullptr) { <<<<<<< HEAD return TX_ERR_NULL_CTX; ← 내가 쓴 것 ======= LOG_ERR("null ctx"); return -1; ← 정식에 들어온 것 >>>>>>> upstream/dev }
VS Code 이 마커를 손으로 지우지 마세요. 파일 위쪽에 뜨는 Resolve in Merge Editor 버튼을 누르면 왼쪽/오른쪽/결과 3분할 화면이 열립니다. 체크박스로 고르면 마커가 알아서 정리됩니다. 마커는 "이게 보이면 아직 해결 안 된 것" 정도로만 알아두면 충분합니다.

고르고 나면 나머지는 평소와 같습니다.

PowerShell
PS> git add src/TxSwitchMngr.cpp PS> git commit # 메시지는 자동으로 채워짐 PS> git push
내 PC → origin
중간에 그만두고 싶다면

git merge --abort — merge 시작 전 상태로 완전히 되돌아갑니다. 충돌이 너무 커서 정리가 안 될 때 언제든 쓰세요. 잃는 것은 없습니다.

텍스트가 합쳐졌다고 끝이 아닙니다

git은 줄 단위로만 봅니다. 위 예에서 양쪽을 다 남기면 문법은 맞지만 동작은 틀립니다. 합친 뒤에는 반드시 빌드하고 동작을 확인하세요. 이건 git이 대신해 주지 않습니다.

06

되돌리기

이 절이 이 문서에서 가장 중요합니다. 되돌릴 수 있다는 걸 알면 나머지를 겁 없이 시도할 수 있습니다.

아직 commit 안 한 수정을 버리고 싶다

PowerShell
PS> git restore src/TxSwitchMngr.cpp # 파일 하나 PS> git restore . # 전부

이건 진짜로 사라집니다. commit 안 한 것은 git이 기억하지 못합니다. 확신이 없으면 아래 stash를 쓰세요.

add를 잘못했다 (staged에서 빼기)

PowerShell
PS> git restore --staged debug_temp.log
VS CodeStaged Changes → Changes로 다시 내려옵니다. 수정 내용은 그대로 있습니다.

방금 commit을 취소하고 싶다 (내용은 남기고)

PowerShell
PS> git reset --soft HEAD~1

commit 기록만 없어지고 고친 내용은 staged 상태로 그대로 남습니다. 메시지를 잘못 썼거나, 파일을 하나 빠뜨렸을 때 쓰면 됩니다. 이미 push한 commit에는 쓰지 마세요.

잠깐 치워두고 다른 일 하기

PowerShell
PS> git stash # 현재 수정을 안전하게 치움 (작업 폴더 깨끗해짐) PS> git stash pop # 다시 꺼냄

P4의 shelve와 가장 비슷합니다. 다만 서버로 가지 않고 내 PC에만 있습니다.

뭔가 크게 잘못됐다

PowerShell
PS> git reflog 0522a5c HEAD@{0}: reset: moving to HEAD~1 4a851e5 HEAD@{1}: commit: ABC-123 null check 2463939 HEAD@{2}: merge upstream/dev

한 번이라도 commit한 것은 거의 다 여기 남아 있습니다. 삭제한 branch도 마찬가지입니다. 돌아가고 싶은 줄의 앞 번호를 찾아서 git reset --hard 4a851e5.

막혔을 때

reflog까지 봤는데 모르겠으면 거기서 멈추고 물어보세요. 추가로 명령을 던지는 것보다, 현재 git status와 git reflog 출력을 그대로 복사해서 보여주는 편이 훨씬 빨리 풀립니다.

07

자주 하는 착각

P4 감각이 그대로 넘어와서 생기는 것들입니다. 여기만 넘기면 나머지는 쉽습니다.

  • commit했으니 제출된 거다 commit은 내 PC에만 기록됩니다. push해야 내 Fork로 가고, PR을 올려야 팀이 봅니다. P4의 submit은 이 셋을 한 번에 하던 것이라 감각이 다릅니다.
  • 고친 파일이 있으니 push하면 올라간다 push는 commit된 것만 보냅니다. 고쳐만 놓고 commit 안 한 파일은 push해도 그대로 내 PC에 남습니다. 성공 메시지가 떠도 마찬가지입니다. 올리기 전에 git status로 확인하는 습관을 들이세요.
  • origin이 정식 저장소다 Fork를 clone했으므로 origin은 내 Fork입니다. 정식은 upstream입니다. branch를 팔 때 origin/dev을 기준으로 삼으면 내 Fork의 오래된 상태에서 시작하게 됩니다.
  • branch를 만드는 건 큰일이다 git branch는 사실상 공짜입니다. 파일 복사가 일어나지 않습니다. 작업 하나에 branch 하나가 정상이고, 하루에 여러 개 만들어도 됩니다.
  • pull이 최신 코드 받는 명령이다 Fork 방식에서 git pull은 기본적으로 내 Fork(origin)를 봅니다. 내 Fork는 자동으로 갱신되지 않으므로 오래된 상태일 수 있습니다. 정식 최신은 git fetch upstream → git merge upstream/dev입니다.
  • 충돌이 났으니 뭔가 망가졌다 충돌은 정상적인 상태입니다. 같은 줄을 두 사람이 고쳤으니 어느 쪽을 쓸지 사람이 정해달라는 뜻일 뿐입니다. git merge --abort로 언제든 시작 전으로 돌아갈 수 있습니다.

clang-format 설정

코드 포맷을 자동으로 맞춰 주는 도구입니다. git과 직접 상관은 없지만, 설정을 잘못하면 diff가 망가져서 리뷰가 불가능해집니다. 그래서 여기 넣었습니다.

먼저 확인

저장소 루트에 .clang-format 파일이 있는지 보세요. 이 파일이 팀의 포맷 규칙입니다. VS Code의 C/C++ 확장(ms-vscode.cpptools)에 clang-format이 들어 있고, 기본 설정이 file이라 이 파일을 자동으로 찾아 씁니다.

설정

.vscode/settings.json에 넣습니다.

.vscode/settings.json
{ "C_Cpp.clang_format_style": "file", "[cpp]": { "editor.defaultFormatter": "ms-vscode.cpptools", "editor.formatOnSave": true, "editor.formatOnSaveMode": "modifications" }, "[c]": { "editor.defaultFormatter": "ms-vscode.cpptools", "editor.formatOnSave": true, "editor.formatOnSaveMode": "modifications" } }
modifications 가 핵심입니다

기본값인 "file"로 두면 저장할 때마다 파일 전체가 재포맷됩니다. 레거시 파일을 세 줄 고쳤는데 diff가 800줄이 되고, 리뷰어는 실제 변경을 찾을 수 없고, merge 충돌이 폭발합니다.

"modifications"는 내가 건드린 줄만 포맷합니다. git이 변경 범위를 알려주기 때문에 동작하는 기능이라, 지금 상황에 정확히 맞습니다.

확인

아무 .cpp를 열고 Shift + Alt + F(Format Document). 오류 없이 들여쓰기가 정리되면 연결된 것입니다. 안 되면 오른쪽 아래 상태바에서 언어 모드가 C++인지 보세요.

포맷에서 빼고 싶은 구간

src/TxSwitchMngr.cpp
// clang-format off static const RegEntry kTable[] = { { 0x0010, "TX_ON", 4 }, { 0x0014, "TX_OFF", 4 }, }; // clang-format on

손으로 정렬을 맞춘 레지스터 테이블처럼, 포맷이 오히려 읽기 나쁘게 만드는 곳에 씁니다.

팀에 공유하려면

.vscode/settings.json을 저장소에 commit하면 팀 전체가 같은 설정을 쓰게 됩니다. 각자 설정하게 두면 반드시 갈라집니다. 다만 이건 저장소 정책이므로 팀 합의 후에 올리세요.

명령 연결 Windows PowerShell 5.1에서는 &&가 동작하지 않습니다. git add . && git commit -m "x" 같은 건 쓰지 말고 한 줄씩 치세요. 어차피 한 줄씩 치는 편이 결과를 확인할 수 있어 낫습니다.
메시지에 따옴표 큰따옴표를 쓰세요. 메시지 안에 큰따옴표가 필요하면 작은따옴표로 감싸면 됩니다.
