Legacy NR Tx 시나리오 기반 SLTE TxMngr UT 작성 방안

문서 목적
Legacy 1900의 NR Tx 동작을 근거로 SLTE TxMngr용 Contract UT를 작성하기 위한 방향, 진행 절차, 스킬 연동 구조 및 향후 스킬 업데이트 필요사항을 협의·정리하기 위해 작성한다.

1. 추진 배경

SLTE 기반 NR Tx 기능을 새로 구현할 때는 Legacy 1900 코드의 동작을 참고해야 한다.

하지만 Legacy 코드를 그대로 SLTE로 복사하는 방식은 적절하지 않다. Legacy와 SLTE는 다음 항목이 다를 수 있기 때문이다.

  • 모듈 구조
  • 클래스와 API 이름
  • 메시지 전달 방식
  • 상태 정보 저장 위치
  • HAL 연동 방식
  • UT Framework와 Mock 구성 방식

따라서 Legacy에서는 기능이 어떤 순서와 조건으로 동작하는지만 추출하고, 실제 구현과 UT는 SLTE 구조에 맞게 다시 Mapping하는 방식이 필요하다.

이번 검토 대상 Feature는 다음과 같다.

DCI-based BWP ID switching에 의한 PCell UL Rank 변경

현재 MSC가 없을 가능성이 있으므로, Legacy SDM 로그와 Legacy 코드를 함께 사용하여 실제 동작 흐름을 확인한다.

2. 최종 목표

이번 작업의 목표는 Legacy 전체 동작을 재현하는 Full UT를 만드는 것이 아니다.

Legacy 시나리오 흐름을 기준으로 Tx 관련 API 경계의 입력과 출력을 정의하고, 이를 SLTE TxMngr의 API 및 모듈에 Mapping하여 SLTE용 UT를 작성한다.

UT에서는 TxMngr 내부 구현 과정을 세부적으로 검증하지 않는다.

입력 메시지 또는 Event 주입
→ SLTE TxMngr 동작
→ 외부 API 호출 여부 확인
→ 전달된 Message 또는 CMD 주요 필드 비교

예를 들어 TxMngr 내부의 private helper 함수가 몇 번 호출됐는지는 검증하지 않는다.

  • SCC로 어떤 메시지가 전송됐는가
  • UL Rank Update API에 어떤 값이 전달됐는가
  • HAL로 어떤 CMD가 전송됐는가

3. 이번 작업에서 제외할 범위

  • Legacy용 UT 작성
  • Legacy 내부 구현 구조를 SLTE에 그대로 복제
  • NR Tx 전체 기능에 대한 Full UT
  • 모든 예외와 복구 절차 검증
  • Transaction 전체 End-to-End 통합 시험
  • Production 코드의 자동 구현
  • Legacy와 SLTE의 함수 이름을 단순 1:1로 연결

Legacy는 동작의 정답을 확인하는 자료로만 사용한다.

실제 UT 대상과 구현 구조는 SLTE TxMngr를 기준으로 한다.

4. 대상 시나리오

BWP ID Switching Event 수신
        │
        ▼
       BCH
        │ PATH_CONFIG_REQ
        ▼
       SCC
        │ PATH_CONFIG_CNF
        ▼
 BCH Message Handler
        │ PCell UL Rank Update
        ▼
   UL Rank 변경 확인
        │ Rank가 실제로 변경된 경우
        ▼
    BCH → HAL CMD

이를 세 개의 UT 검증 구간으로 나눈다.

검증 구간입력출력
1BWP ID Switching EventSCC PATH_CONFIG_REQ
2SCC PATH_CONFIG_CNFPCell UL Rank Update API
3PCell UL Rank 변경HAL CMD

세 구간을 하나의 긴 UT로 만들지 않고 각각 독립된 UT로 만드는 것을 기본으로 한다. 이렇게 해야 UT가 실패했을 때 문제가 발생한 위치를 쉽게 구분할 수 있다.

5.2 Legacy API 경계의 UT 검증 포인트 정의

Legacy 함수 이름을 그대로 UT 기준으로 사용하지 않는다. 각 단계에서 외부에서 관찰할 수 있는 입력과 출력으로 검증 포인트를 정의한다.

VP-01: PATH_CONFIG_REQ 전송

항목내용
TriggerBCH가 Target BWP ID를 포함한 BWP ID switching event를 수신
입력PCell ID, Current BWP ID, Target BWP ID, Target BWP의 UL Rank, Current UL Rank
기대 출력SCC로 PATH_CONFIG_REQ 전송
검증 필드Message ID, Cell ID, Target BWP ID, UL Rank
제외 필드Timestamp, Reserved, Padding, Runtime 자동 생성 값

VP-02: PATH_CONFIG_CNF 이후 UL Rank Update

항목내용
TriggerBCH가 성공한 PATH_CONFIG_CNF 수신
입력Result, PCell ID, Target BWP ID, Confirmed UL Rank
기대 출력PCell UL Rank Update 기능 호출
검증 항목호출 여부, PCell ID, BWP ID, UL Rank

VP-03: UL Rank 변경 후 HAL CMD 전송

항목내용
TriggerPCell UL Rank가 기존 값과 다른 값으로 갱신
입력Previous Rank, Updated Rank, Target BWP ID, PCell ID
기대 출력BCH 또는 TxMngr가 HAL로 Rank 변경 CMD 전송
검증 필드HAL CMD ID, Cell ID, Target BWP ID, Updated UL Rank

5.3 Legacy 검증 포인트를 SLTE TxMngr에 Mapping

Legacy 함수와 SLTE 함수를 이름으로 연결하지 않고, 책임을 기준으로 Mapping한다.

Legacy 책임:
Target BWP의 Rank를 포함한 PATH_CONFIG_REQ 전송

SLTE 책임:
동일한 입력을 받아 SCC 연동 메시지를 생성하고 전송하는 TxMngr API
검증 ID시나리오 책임Legacy 근거SLTE 대상UT 입력 방식UT 출력 검증
VP-01BWP switching 후 PATH_CONFIG_REQ 전송BCH event handlerTxMngr BWP switching entryEvent/API 호출SCC Mock 메시지 비교
VP-02PATH_CONFIG_CNF 이후 Rank 갱신BCH CNF handlerTxMngr CNF handlerCNF 메시지 주입Rank Update API 호출 인자
VP-03Rank 변경 후 HAL CMD 전송BCH HAL send 경로TxMngr 또는 HAL AdapterRank 변경 입력HAL Mock CMD 비교

직관적 Mapping 예시: SLTE TxMngr가 Legacy BCH 역할을 직접 담당하는 경우

아래 예시는 Legacy의 BCH 모듈을 SLTE에서도 그대로 만들자는 의미가 아니다. Legacy BCH가 담당하던 책임을 SLTE에서는 TxMngr가 직접 수행하는 경우를 보여준다.

Legacy 흐름

BWP Switching Event
    ↓
Legacy BCH event handler
    ↓
PATH_CONFIG_REQ 생성 및 SCC 전송
    ↓
PATH_CONFIG_CNF 수신
    ↓
Legacy BCH CNF handler
    ↓
UL Rank Update
    ↓
HAL CMD 전송


SLTE Mapping 예시

BWP Switching Event
    ↓
TxMngr::handleBwpSwitch(...)
    ↓
TxMngr 또는 SCC Adapter가 PATH_CONFIG_REQ 전송
    ↓
TxMngr::handlePathConfigCnf(...)
    ↓
TxMngr가 PCell UL Rank 상태 갱신
    ↓
TxMngr 또는 HAL Adapter가 HAL CMD 전송
Legacy 책임Legacy 위치 예시SLTE Mapping 예시UT 검증 방법
BWP switching event 처리Legacy BCH event handlerTxMngr::handleBwpSwitch()Event를 TxMngr에 주입한 뒤 SCC로 전송된 PATH_CONFIG_REQ 비교
PATH_CONFIG_CNF 처리Legacy BCH CNF handlerTxMngr::handlePathConfigCnf()CNF를 TxMngr에 주입한 뒤 UL Rank Update API 호출 인자 확인
Rank 변경 후 HAL 전송Legacy BCH HAL send 경로TxMngr 또는 HalAdapter::sendTxConfig()Rank 변경 입력 후 HAL Mock에 전달된 CMD 필드 비교
중요: Legacy의 BCH 클래스나 함수명을 SLTE에 그대로 복제하는 것이 아니라, Legacy BCH가 담당했던 시나리오 책임을 SLTE TxMngr의 기존 또는 신규 API에 배치하는 것이다.

SLTE에 대응 API가 아직 없으면 억지로 기존 API에 연결하지 않고 MISSING 또는 PARTIAL로 기록한다. 이 항목이 구현 담당자의 실제 구현 대상이 된다.

상태의미
MAPPEDSLTE에 대응 API 또는 모듈이 존재
PARTIAL일부 기능만 존재하고 추가 구현 필요
MISSING대응 기능이 없어 새 구현 필요
NOT_APPLICABLESLTE 구조상 별도 Mapping이 필요하지 않음
NEED_REVIEW담당자와 설계 협의 필요

5.4 현재 SLTE UT 구조 확인

  • TxMngr Fixture와 SetUp/TearDown 방식
  • BWP switching Event 또는 메시지 주입 방법
  • SCC 송신 API Mock/캡처 방법
  • PATH_CONFIG_CNF 주입 방법
  • UL Rank Update API Mock 방법
  • HAL CMD 송신 API Mock 방법
  • jomock 사용 방식
  • Message 구조체 비교 helper
  • 유사 Test Case
  • UT Build 및 실행 방법

Jomock은 TxMngr의 외부 Dependency를 제어하고 검증하는 용도로 사용한다.

  • SCC Message Sender
  • HAL Command Sender
  • Rank Configuration Provider
  • Tx Context 또는 Rank Update Interface
  • 외부 DB 조회 결과

반대로 buildPathConfigReq(), getMappedRank(), updateInternalState() 같은 내부 helper는 가급적 Mock하지 않는다.

5.5 실제 SLTE UT 구조를 학습한 뒤 UT Specification 작성

중요: TEST_F(...)는 설명용 예시일 뿐 실제 생성 형식이 아니다. 대상 SLTE TxMngr UT 폴더에서 Test 선언, Fixture, Jomock, input 주입, output 비교 문법을 먼저 학습하고 승인된 형식만 사용한다.
<ACTUAL_TEST_DECLARATION_FROM_APPROVED_UT_PROFILE>(
    <ACTUAL_FIXTURE_OR_SUITE>,
    <CASE_NAME_FOR_VP_01>)
{
    <ACTUAL_INPUT_INJECTION_PATTERN>
    <ACTUAL_JOMOCK_OR_EXTERNAL_API_EXPECTATION>
    <ACTUAL_MESSAGE_FIELD_COMPARATOR>
}

VP-01: BWP switching input → PATH_CONFIG_REQ output 검증
VP-02: PATH_CONFIG_CNF input → PCell UL Rank Update API 검증
VP-03: UL Rank changed input → HAL CMD output 검증

실제 선언 token과 문법은 ut_structure_profile.json 및 승인된 Knowledge Manager UT profile을 기준으로 채운다. 프로파일에 없는 TEST_F, Fixture, Mock, Assertion 문법은 사용하지 않는다.

필드 값 Assert 필수 규칙

각 Verification Point는 외부 API/Mock 호출 검증에 더해 최소 1개 이상의 실제 필드 값 assert를 포함해야 한다. 호출 여부만 검증하는 UT는 미완성으로 간주한다.

VP호출 검증필수 값 검증값 근거
VP-01SCC sender 호출Message ID / Cell ID / Target BWP ID / UL Rank 중 최소 1개Legacy SDM 또는 code field probe
VP-02Rank Update API 호출PCell ID / BWP ID / 적용 UL Rank 중 최소 1개Legacy SDM 또는 code field probe
VP-03HAL sender 호출HAL CMD ID / Cell ID / Target BWP ID / Updated UL Rank 중 최소 1개Legacy SDM 또는 code field probe
중요: assert 기대값은 추정해서 고정하지 않는다. Legacy SDM 또는 코드/field probe에서 확인되지 않은 값은 NEED_REVIEW로 남기며, validator가 문법적으로 PASS하더라도 의미 검토 전에는 UT를 승인하지 않는다.

5.6 Negative UT 결정

Negative UT는 추정으로 작성하지 않고 Legacy SDM 또는 코드에서 동작이 확인된 경우에만 추가한다. Test 선언 형식은 Positive UT와 동일하게 승인된 실제 UT 프로파일에서 가져온다.

<ACTUAL_TEST_DECLARATION_FROM_APPROVED_UT_PROFILE>(...FailedCnf...)
→ PATH_CONFIG_CNF 실패 시 Rank Update API 미호출 검증

<ACTUAL_TEST_DECLARATION_FROM_APPROVED_UT_PROFILE>(...RankUnchanged...)
→ Rank 동일 시 HAL CMD 미전송 검증

<ACTUAL_TEST_DECLARATION_FROM_APPROVED_UT_PROFILE>(...InvalidBwp...)
→ Invalid BWP 처리 검증

7.1 자동화 수준과 실제 공수

전체 과정이 모두 자동화되는 것은 아니다. 특히 Legacy → SLTE Mapping과 필드 assert의 정답 결정은 사람의 아키텍처·도메인 판단이 필요하며, 실제 공수가 가장 큰 구간이다.

단계자동화 수준담당실제 공수
SDM 파싱자동sdm-parser낮음
Legacy flow/field 추출자동code-analyzer flow/field probe중
VP 정의수작업(근거는 자동)사람 + code-analyzer 근거높음
Legacy → SLTE Mapping수작업(자동 추론 없음)사람 + Mapping 지식 저장가장 높음
사내 UT 구조 습득자동code-analyzer낮음
Contract UT 골격 생성반자동code-fix중
UT 필드 assert 작성/정답 검토수작업사람 + Legacy 근거높음
문법·스코프 검증자동code-fix낮음
Legacy 쪽 근거는 field probe가 제공할 수 있지만 SLTE 대응 API/필드의 최종 결정은 사람이 수행한다. MAPPED / PARTIAL / MISSING / NOT_APPLICABLE / NEED_REVIEW 상태를 사용하고 Mapping 리뷰 시간을 별도로 확보한다.

업무 분담Legacy 분석, SLTE Mapping 검토, UT/Jomock 검토, Production 구현, UT Review 담당. Legacy → SLTE Mapping은 책임 기준 수작업이며 전체 과정에서 가장 공수가 큰 단계이므로 담당과 리뷰 시간을 별도로 확보한다.

9. 성공 기준

  • Legacy 시나리오 순서가 SDM과 코드 근거로 확인됨
  • VP-01~VP-03의 입력과 출력이 정의됨
  • 각 검증 포인트의 SLTE TxMngr 대응 위치가 확인됨
  • MAPPED / PARTIAL / MISSING 상태가 구분됨
  • SCC, Rank Update, HAL 경계가 Jomock으로 검증됨
  • 내부 private helper에 과도하게 결합하지 않음
  • 신규 UT PASS
  • 기존 NR Tx UT Regression PASS
  • 최종 As-built Mapping이 지식매니저에 업데이트됨
  • 각 VP는 mock/API 호출 검증에 더해 최소 1개 이상의 필드 값 assert를 포함함
  • assert 기대값은 Legacy SDM 또는 코드/field probe에서 확인된 실제 근거를 사용함
  • 호출 여부(.Times 등)만 검증하고 필드 값 비교가 없는 UT는 미완성으로 반려함
  • contract-ut-validate PASS와 별도로 필드 assert의 의미 정확성을 사람이 검토함

11. 최종 제안

Legacy SDM과 코드는 시나리오 및 기대 동작의 근거로 사용한다.
Legacy 시나리오에서 API 경계별 UT 검증 포인트를 정의한다.
검증 포인트를 SLTE TxMngr의 책임과 API에 Mapping한다.
현재 SLTE UT Fixture와 Jomock Pattern을 사용해 입력을 주입하고 외부 출력을 비교하는 Contract UT를 작성한다.
UT와 Mapping 문서를 구현 기준으로 사용하며, 신규 UT와 기존 Regression을 모두 통과시킨다.

Legacy UT는 작성하지 않는다.

Legacy 구현 구조를 SLTE에 복제하지 않는다.
