## 3. 먼저 동의를 구하는 전제 — 현재 설계의 핵심 결정은 옳습니다

제안에 들어가기 전에 분명히 합니다. 아래 두 결정은 규모 문제의 정답에 해당하고, 바꾸지 말 것을 제안합니다.

1. **T-LLM의 분업.** LLM이 탐색하지 않고 결정형 코드가 탐색한다는 원칙입니다. 2천 파일 규모에서 가장 중요한 결정이며 이미 올바른 쪽으로 고정되어 있습니다.
2. **전체 주입 금지.** 야간 분석 r0001 §3-3의 `전체 저장소를 LLM에 한 번에 주입하지 않는다`입니다.

아래 제안은 이 두 결정을 **대체하는 것이 아니라 그 안에서 검색 정밀도를 올리는 것**입니다.

## 4. 판정 요청 — A군: 규모 확대의 선행 조건

### A1. T-PROBE의 budget 우회 수정을 규모 확대의 선행 조건으로 승격할 것

- **지칭 대상**: T-PROBE (v0.15.4 `probe_engine.py`의 callers/callees), 그리고 그것을 고친 T-CA5.
- **실패 조건**: T-SCOPE를 수십 파일에서 수백~수천 파일로 넓힌 상태에서 T-CA4를 그대로 쓰는 경우.
- **근거**: 설계 GPT가 Qwen 구현 인계 r0001 §9에서 직접 확인했습니다. callers/callees가 선택 파일 budget을 우회하고, 누락·불량 line anchor도 CONFIRMED로 반환합니다.
- **왜 규모에서 성격이 달라지는가**: 프로토콜 스택의 caller/callee fan-out은 메시지 핸들러·dispatch·콜백 때문에 급격히 커집니다. budget 우회는 파일 수십 개에서는 비효율이지만, 수천 개에서는 한 번의 probe가 광범위하게 번지면서 **그 결과가 CONFIRMED 라벨을 달고 산출**됩니다. 저사양 LLM은 그 라벨을 검증할 수 없고, Updater는 라벨을 보존하도록 설계되어 있습니다. 즉 오라벨이 지식 후보까지 그대로 전달됩니다.
- **제안**: 야간 분석 r0001 §4의 "야간 활성화 조건" (A)~(E)에 **(F) T-PROBE 계열 결함의 수정본이 활성 설치본에 반영되어 있을 것**을 추가. T-CA5의 전체 suite·독립 코드 리뷰·Linux 설치/호출이 현재 NOT_RUN이므로, 그 게이트를 통과한 뒤 확대합니다.
- **검증 방법**: 동일 source pin에서 선택 파일 수를 N개로 고정하고 probe를 호출해, 실제 열린 파일 수가 N을 넘지 않는지와 anchor 없는 edge가 CONFIRMED로 나오지 않는지 확인. T-CA5가 추가한 `probe_meta.coverage_partial`, `unanchored_edge_count`로 관측.
- **필요 승인**: T-CA5의 격리 회귀·독립 리뷰·설치는 기존 게이트대로 별도 승인. 이 제안은 **게이트 순서의 변경만** 요청하며 설치를 요청하지 않습니다.
- **증거 수준**: 결함 자체는 설계 GPT의 E1~E2 기술. 규모에서의 영향은 제 예측(E0).

### A2. T-SCOPE의 분모를 먼저 확정할 것

- **지칭 대상**: T-SCOPE (4개 모듈과 215행) 대 사용자 구술 전제(약 2천 파일·수십 폴더).
- **실패 조건**: 1차 대상이 4개 모듈인지 Layer1 전체인지 합의되지 않은 상태에서 A군·B군을 판정하는 경우. 판정의 타당성이 분모에 따라 달라집니다.
- **근거**: 야간 분석 r0001 §2는 담당을 4개 모듈로 한정하고 Search/Measurement·DRX 본체·Paging을 자동 포함하지 않습니다. 사용자가 말한 2천 파일은 Layer1 폴더 전체로 읽힙니다.
- **제안**: 설계 GPT가 1차 대상 분모를 다음 중 하나로 명시. (a) T-SCOPE 4개 모듈에 해당하는 파일 집합만, (b) Layer1 전체. 그리고 폴더 경계와 모듈 경계가 일치하는지도 G0 확인 항목으로 둡니다. **폴더 40개가 모듈 40개라고 가정하지 않습니다.**
- **왜 중요한가**: (a)이면 유효 파일 수가 크게 줄어 현행 설계로도 가능성이 높아집니다. (b)이면 A1·B1이 사실상 필수가 됩니다.
- **필요 승인**: 없음. 문서상 범위 확정입니다.

## 5. 판정 요청 — B군: 검색 정밀도 구조 제안

### B1. T-PROBE-RE의 dispatch·매크로 간선 결손을 "측정으로" 확정할 것

- **지칭 대상**: T-PROBE-RE (정규식 + bounded 탐색 방식).
- **실패 조건**: Module별 함수 목록은 그럴듯하게 나오지만 **Procedure 흐름(REQ/CNF/IND 순서)이 비어 있거나 얕은** 산출물이 반복되는 경우. 사용자가 원하는 것은 후자입니다.
- **근거와 한계**: CoWork code-analyzer 야간 재사용 검토 r0001은 "기능 부족이라는 증거 없이 새 AST/GraphDB를 추가하면 중복 비용·회귀 위험"이라며 `REUSE / NO_CHANGE`로 판정했습니다. **그 판정 자체에 이견이 없습니다.** 다만 그 판정의 전제인 "증거가 없다"를 해소할 측정이 아직 한 번도 실행되지 않았습니다(같은 문서 §4에서 실제 L1 코드 정확도 `NOT_RUN`).
- **왜 L1에서 특히 문제인가**: 지식의 핵심이 하필 정규식이 약한 구조 위에 있습니다. 메시지 핸들러 등록 테이블, 함수 포인터 dispatch, `#ifdef` feature 분기, 테이블 주도 상태 기계, 별도 정의·생성 파일의 IPC 메시지 ID, 템플릿·오버로드입니다. Procedure 뷰는 정확히 이 간선들 위에 성립합니다.
- **제안**: 아래 §8의 비교 측정을 1회 실행해 `PROVEN_CODE_GAP` 여부를 확정. 차이가 유의미하지 않으면 **B2~B3을 기각하고 NO_CHANGE를 유지**합니다. 이 제안은 결론이 아니라 결론을 만드는 절차입니다.
- **증거 수준**: 결손 가설은 제 예측(E0). 탐색 방식 기술은 설계 GPT의 E2.

### B2. 결정형 심볼·간선 인덱스를 "파생 캐시"로 도입할 것

- **지칭 대상**: T-PROBE-RE를 보완하는 입력 인덱스. **T-CA4/T-CA5의 action·schema 변경을 요청하지 않습니다.**
- **제안 내용**: tree-sitter C++ 파서로 1회 결정형 인덱싱. 산출은 SQLite 테이블 3개 (`symbols`, `edges`, `guards`). 내용은 §7에서 실제로 확인한 범위입니다.
- **기존 금지 규칙과의 정합성 논증** — 가장 중요한 부분입니다. 야간 분석 r0001 §1은 `새 그래프 DB·RAG 엔진·C++ 파서·분석 원장·스키마를 선제 생성하지 않는다`입니다. 제안이 이에 저촉되지 않는 근거를 제시합니다.
  - **원장이 아닙니다.** Work·Evidence·지식·승인·영수증을 담지 않습니다. 정본은 Kernel과 개인/그룹 지식에 그대로 남습니다.
  - **소스에서 언제든 재생성됩니다.** 삭제 후 재구축이 가능하고, 손실 시 복구 절차가 "다시 돌린다"입니다. SSOT가 아닙니다.
  - **RAG가 아닙니다.** 임베딩·벡터 검색이 없고, 모델에 직접 입력되지 않습니다. 기존 probe의 입력 후보를 좁히는 데만 씁니다.
  - **다만 "선제 C++ 파서 생성"에는 형식상 걸립니다.** 그래서 B1의 측정 없이 도입을 요청하지 않습니다. 저는 **B1 → (결손 확정 시) → B2** 순서를 제안합니다.
- **라이선스**: tree-sitter는 MIT, tree-sitter의 C++ 문법도 MIT입니다. CoWork 저사양 LLM 연구·QA r0001이 이미 tree-sitter MIT와 scip-clang Apache-2.0을 확인했고 CodeQL은 `EXCLUDE_RUNTIME`으로 판정했습니다. **이 제안은 그 판정을 유지하며 CodeQL을 포함하지 않습니다.** 외부 소스·바이너리·가중치 복사는 0입니다.
- **상한을 올리는 선택지**: 빌드에서 `compile_commands.json`을 얻을 수 있으면 clangd 인덱스 또는 scip-clang으로 매크로·템플릿·오버로드를 정확히 해석할 수 있습니다. 이것이 §7 한계의 근본 해결입니다. **빌드에서 compile DB 생성이 가능한지가 G0 확인 항목**입니다. 저는 확인하지 못했습니다.
- **검증 방법**: 동일 source pin에서 (a) 인덱스 구축 시간·크기, (b) 재구축 시 동일 결과(결정성), (c) 인덱스를 거친 probe 입력이 실제로 좁아졌는지, (d) 기존 산출물 무퇴행.
- **필요 승인**: 사내 소스 읽기 권한과 패키지 설치(오프라인이면 wheel 2개). 실제 구축은 승인 전 실행하지 않습니다.

### B3. dispatch·메시지 테이블 추출을 명시적 규칙으로 둘 것

- **지칭 대상**: 핸들러 등록 테이블에서 `message ID → handler` 간선을 만드는 결정형 규칙. B1에서 결손이 확정된 경우의 **최소 EXTEND 후보**입니다.
- **근거**: §7에서 확인했듯 `&Class::method` 형태의 테이블 등록은 인덱싱으로 잡히지만, **어떤 메시지 ID가 어떤 핸들러로 가는지의 연결은 자동으로 생기지 않습니다.** 테이블 항목 구조를 읽는 규칙이 별도로 필요합니다.
- **제안**: 테이블 형태별로 좁은 규칙을 두고, 규칙이 매칭되지 않은 테이블은 **UNKNOWN으로 명시**합니다. 추정으로 메우지 않습니다. 이것이 야간 분석 r0001 §3-4의 `조건 미상·CNF ambiguity·빌드 미확인은 UNKNOWN/RN로 보존`과 일치합니다.
- **필요 승인**: 실제 코드 변경은 재현 가능한 결함 근거와 회귀시험 후 기존 배포 게이트.

### B4. anchor 재검증을 결정형 스크립트로 둘 것

- **지칭 대상**: LLM 산출물의 모든 CONFIRMED 주장.
- **실패 조건**: 저사양 LLM이 존재하지 않는 파일·라인 anchor를 붙여 CONFIRMED로 서술하는 경우. Qwen R1 리뷰 결과 §4.1이 같은 위험을 "provenance 누락 시 근거 없이 서술 보강(padding)"으로 가설화했고 상태는 UNKNOWN입니다.
- **제안**: 각 CONFIRMED에 대해 스크립트가 해당 파일·라인을 열어 심볼 존재를 확인하고, 불일치는 자동 강등. 모델 호출이 전혀 필요 없고, 환각 anchor라는 최대 실패 모드를 구조적으로 차단합니다. T-CA5의 `unanchored_edge_count`가 이미 같은 방향입니다.
- **제안 반영 위치**: Qwen 구현 인계 r0001 §6 "합격 조건" 표의 `CONFIRMED fact의 source anchor 누락 0건`을 **선언이 아니라 기계 검사로** 바꾸는 것입니다.
- **필요 승인**: 없음(읽기 전용 검사). 기존 가이드에 문구 추가 여부는 설계 GPT 판정.

## 6. 판정 요청 — C군: 멀티에이전트와 처리량

### C1. 역할 분할형 멀티에이전트는 권하지 않습니다

사용자가 물은 "멀티 에이전트 방식"에 대한 제 판단입니다. **저사양 모델에서는 역효과가 클 가능성이 높습니다.**

- **provenance가 인계 지점에서 떨어집니다.** 이 설계의 안전성은 CONFIRMED/INFERRED/UNKNOWN 라벨과 anchor에 있습니다. 에이전트 간 대화 인계는 뒷 에이전트가 앞 에이전트의 서술을 사실로 받는 구조이고, INFERRED가 CONFIRMED로 조용히 승격되는 경로가 생깁니다. Qwen R1 리뷰의 G0-7(새 근거 없는 승격 0)이 막으려던 것이 정확히 이것입니다.
- **재현성이 깨집니다.** 같은 source pin에 같은 CONFIRMED 집합이 나와야 합니다(야간 분석 r0001 T02, Qwen R1 §4.5 G0-7). 다중 에이전트 대화는 비결정적입니다.
- **병목이 아닌 곳을 늘립니다.** 병목은 추론 병렬성이 아니라 검색 정밀도(B1)입니다. 에이전트를 늘려도 정규식이 못 보는 dispatch 간선은 여전히 안 보입니다.

### C2. 확대 단계의 병렬화는 "단위 병렬"로 명시할 것

- **지칭 대상**: 야간 분석 r0001 §4 "초기 배치: 대표 시나리오 1개, 품질·중복·결과 readback 검증 후에만 점진 확대".
- **문제**: 확대 방식이 적혀 있지 않습니다. 215행을 1건씩 처리하면 매우 긴 기간이 걸리고, 그 압력이 확대 시점에 다시 멀티에이전트 유혹으로 돌아옵니다.
- **제안**: 확대를 **서로 독립인 시나리오 K개의 동시 실행**으로 정의. 각 실행은 자기 bounded bundle만 보는 별도 프로세스이고 상태를 공유하지 않습니다. 멀티 프로세스이며 멀티 에이전트 대화가 아닙니다. 기존 §4의 Budget·fail-closed·중복 금지 규칙을 그대로 적용하고, 동일 입력 재호출 0과 Job ID 재큐잉 0을 유지합니다.
- **필요 승인**: 실제 동시 실행 수와 예약은 기존 야간 활성화 게이트.

### C3. 역할을 나눌 경우의 유일한 권고 패턴

멀티에이전트를 쓰기로 판정한다면, 제가 유일하게 권하는 형태입니다.

- **추출기**: 소스를 읽고 anchor 붙은 facts 파일만 씁니다.
- **서술기**: facts 파일만 읽습니다. **소스 접근 권한이 없습니다.**

서술기는 anchor를 만들어낼 수 없습니다. 파일을 볼 수 없기 때문입니다. 프롬프트로 금지하는 것이 아니라 권한 구조로 보장됩니다. 역할은 둘까지만 두고, 인계는 대화가 아니라 파일로 합니다.

## 7. 제가 사외 PC에서 실제로 실행한 것과 그 한계

B1~B3의 전제를 스스로 확인하기 위해 **합성 데이터로만** 돌렸습니다. 회사 소스는 사용하지 않았습니다.

- 환경: 사외 Windows PC, 임시 venv. `tree-sitter 0.27.0`, `tree-sitter-cpp 0.23.4`. 컴파일러 없이 wheel 설치.
- 입력: **제가 직접 작성한 합성 C++ 1파일.** 핸들러 테이블, `#ifdef` feature 가드, 멤버 함수 포인터 dispatch를 모사했습니다.
- 추출 방식: 노드 순회로 `function_definition`(심볼), `call_expression`(호출 간선), `&`로 시작하는 `pointer_expression`(테이블 등록 간선), `preproc_ifdef`/`preproc_if`(가드 범위).

**확인된 것**

- 함수 심볼이 파일·시작/끝 줄과 함께 추출됨.
- 함수 본문 내 호출 간선이 줄 번호와 함께 추출됨.
- `#ifdef FEATURE_...` 가드의 줄 범위가 추출됨.
- 파일 범위 핸들러 테이블의 `&Class::method` 등록이 추출됨. **단, 첫 시도에서는 누락**되었습니다. 함수 밖에 있어 호출자가 없었기 때문이며, 파일 범위를 별도로 표기하는 수정으로 잡혔습니다. 이 종류의 경계 실수가 나기 쉽다는 실례입니다.

**확인된 한계 — B3이 필요한 이유**

- 멤버 함수 포인터 호출은 `(this->*h.fn)(m)` 같은 식으로만 남고, **그 호출이 실제 어느 핸들러를 가리키는지는 연결되지 않습니다.**
- 따라서 `메시지 ID → 핸들러`는 테이블에서 `&핸들러`를 뽑는 데까지만 자동이고, 그 이상은 B3의 규칙이 필요합니다.
- 매크로 전개, include 해석, 오버로드 구분, 템플릿 인스턴스화를 풀지 못합니다. 호출은 **이름으로만** 이어지므로 동명 함수는 모호합니다.
- 매크로나 코드 생성으로 만들어진 테이블은 보이지 않습니다.

**실행하지 않은 것**: 실제 Layer1 소스 인덱싱, 성능·규모 실측, 사내 환경 설치 가능성, probe와의 비교 측정.

## 8. B1을 해소할 측정 설계 — 제안하는 다음 한 동작

모델 호출이 필요 없고, 결과가 어느 쪽이든 현재 교착을 해소합니다.

- **대상**: T-SCOPE 안에서 이미 선정된 대표 시나리오(NR L1 Tx → UL Tx Switching)와 관련 함수 **5개**. 새 시나리오를 만들지 않습니다.
- **고정**: 동일 source pin, 동일 선택 파일 집합.

| 측정 | 방법 | 판정 |
|---|---|---|
| M1 인덱스 구축 비용 | 실제 대상 폴더에 결정형 인덱싱 1회. 모델 호출 0 | 시간·크기 실측 |
| M2 간선 비교 | 함수 5개의 caller/callee를 현행 probe와 인덱스에서 각각 산출 | 차집합의 크기와 성격 |
| M3 dispatch 누락 | 담당자가 이미 아는 핸들러 등록 1~2건이 각각에서 잡히는지 | 잡힘/누락 |

- **판정 규칙**: M2·M3에서 현행 probe가 놓친 간선이 유의미하면 B1을 `PROVEN_CODE_GAP`으로 확정하고 B2·B3을 검토합니다. 유의미하지 않으면 **B2·B3을 기각하고 기존 `REUSE / NO_CHANGE` 판정을 유지**합니다.
- **기존 다음 행동과의 관계**: 야간 분석 r0001 §6과 code-analyzer 재사용 검토 r0001 §4의 다음 행동(설치본 G0 → 대표 1건 검증)을 대체하지 않습니다. 다만 G0만으로는 "정규식이 충분한가"에 답할 수 없으므로 **이 측정을 같은 라운드에 포함**할 것을 제안합니다.
- **필요 승인**: 사내 소스 읽기, 인덱싱 패키지 설치. 그 외 쓰기·게시·예약·모델 호출은 포함하지 않습니다.

## 9. 판정 요청 — D군: 문서·실행 환경 정합성

### D1. T-R0005와 T-QWEN의 중지 조건 충돌 해소

- **문제**: T-R0005는 `소스/설치 스킬 수정 금지`이고 "이번 범위의 충돌 조건은 이 r0005를 우선"이라고 선언합니다. T-QWEN은 "G0 조사만 하고 종료하지 말고 … 확인된 누락만 최소 보완·관련 회귀시험까지 수행"입니다. `handoffs/README.md`의 Updater 표에서 r0005는 여전히 "현재 인계"로 표시됩니다.
- **실패 조건**: 업무 GPT에 두 문서가 함께 입력되는 경우. 어느 쪽을 따를지 결정할 근거가 문서 안에 없고, r0005의 우선 선언 때문에 보수적으로 멈출 수도 있습니다.
- **제안**: T-QWEN에 r0005와의 관계를 한 줄 명시(대체인지, 특정 범위에서만 우선인지, 병행인지). MCP 인계 r0002가 r0001에 대해 "그 범위에서 r0001보다 우선"이라고 쓴 방식이 선례입니다.
- **필요 승인**: 없음. 설계 GPT의 문서 결정 사항입니다.

### D2. OpenCode를 consumer profile로 명시

- **지칭 대상**: T-ARCH의 OpenCode 구간. `.claude/skills`를 그대로 사용합니다.
- **문제**: `handoffs/`의 어느 문서에도 OpenCode 실행 환경 검토가 없습니다. CoWork 운영 지식은 이미 "OpenCode·Roo Code·사내 LLM … 저사양 Qwen3.6-27B 사용 이력도 있어 **명확한 지시와 작은 입력 단위를 중시**한다"고 적고 있습니다.
- **확인 요청 항목**:
  1. **스킬 지시문 크기 대 저사양 모델의 지시 수행력.** T-R0005는 41,825 B이고 G01~G14, KR-01~14, T01~T24, 8개 독립 상태축을 담습니다. 이 밀도의 제약을 저사양 모델이 끝까지 유지할 수 있는지 확인이 필요합니다. 본문과 실행 체크리스트의 분리를 제안합니다.
  2. **도구 이름·서브에이전트 패리티.** 특정 하네스의 도구 집합을 전제로 쓰인 지시가 OpenCode에서 조용히 무시될 수 있습니다. C1·C3의 판단과 직결됩니다.
  3. **스킬 자동 선택.** `description` 기반 자동 선택은 저사양 모델에서 오선택이 잦습니다. 야간 배치에서는 명시 호출을 제안합니다.
  4. **fail-closed 게이트의 위치.** `may_invoke_doc_converter=false`, `may_publish_knowledge=false`는 현재 helper 쪽에 있습니다. **하네스를 옮길 때도 모델 지시문이 아니라 코드에 남아 있어야** 합니다. 승인 모델이 다른 환경으로 이동할 때 가장 깨지기 쉬운 부분입니다.
- **제안**: 위 4개를 G0 확인 항목으로 추가하고, OpenCode를 기존 consumer profile 목록에 명시적으로 포함.
- **필요 승인**: 없음.

### D3. 품질 임계치의 자리를 측정 설계와 함께 유지

- **지칭 대상**: Qwen R1 리뷰 MAJOR-1(얕은 출력의 정량 기준 부재)과 그에 대한 설계 GPT 판정(ACCEPT, "데이터 기반 임계값은 대표 사례 후 합의").
- **제안**: 그 판정을 유지하되, §8의 M1~M3이 **임계치 역산에 쓸 첫 데이터**가 됨을 문서에 연결. 임계치를 지금 숫자로 확정하자는 제안이 아닙니다.
- **필요 승인**: 없음.
