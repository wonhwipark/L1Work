P4 → GitHub 전환용 빠른 이해 가이드

P4 사용자 관점에서 이해하는
Git Commit · Push · PR · Merge

가장 먼저 기억할 핵심은 하나입니다. P4의 Shelve는 Git의 Commit 하나와 같지 않습니다. 실무적으로는 Feature Branch에서 Commit 후 Push한 상태가 P4 Shelve에 가장 가깝습니다.

1. 한 줄로 이해하기

P4
Shelve

변경을 서버에 올려 보관하거나 리뷰 가능하게 만드는 상태.

Git / GitHub
Commit + Push

Feature branch의 변경 기록을 GitHub 서버까지 올린 상태.

핵심
가장 가까운 대응

P4 Shelve ≈ Git Feature Branch Commit + Push

기억법: Commit은 “내 PC에 변경 이력 저장”, Push는 “GitHub 서버에 올리기”, PR은 “리뷰 요청”, Merge는 “공식 브랜치 반영”입니다.

2. P4 ↔ Git/GitHub 개념 비교

P4에서 익숙한 개념 Git / GitHub에서 가까운 개념 쉽게 설명하면
Workspace Local Working Tree 내 PC에서 실제 파일을 수정하는 작업 공간
Pending CL Working Tree / Staging / Local Commit 아직 공식 브랜치에는 반영되지 않은 내 변경 작업
Shelve Feature Branch Commit + Push 변경을 서버에 보관하고 다른 사람이 확인할 수 있는 상태
Code Review Pull Request(PR) Review 내 branch 변경을 target branch에 넣기 전 리뷰받는 단계
Submit PR Merge 리뷰 완료 후 공식 target branch에 변경을 실제 반영
Unshelve Checkout / Cherry-pick / 다른 branch 내용 가져오기 다른 곳에 저장된 변경을 내 작업으로 가져오는 행위

3. 왜 Commit 하나가 Shelve와 같지 않은가?

P4 Shelve

서버에 존재

일반적으로 서버에 저장되므로 다른 개발자가 확인하거나 리뷰에 활용할 수 있습니다.

서버 저장 공유 가능 리뷰 가능
VS
Git Commit

기본적으로 내 PC에 존재

git commit만 하면 변경 이력이 내 로컬 repository에 기록됩니다. 아직 GitHub에는 올라가지 않았습니다.

로컬 저장 아직 공유 안 됨
내 PC feature/JIRA-1234 └─ commit ABC123 GitHub 서버 └─ 아직 없음 ↓ git push GitHub 서버 feature/JIRA-1234 └─ commit ABC123 → 이 시점부터 P4 Shelve와 훨씬 비슷해짐

5. 리뷰 중 수정하면 PR을 다시 만들어야 하나?

아니요. 같은 feature branch에 수정 후 commit하고 push하면, 기존 Pull Request에 새 변경이 자동으로 추가됩니다.
feature/JIRA-1234 commit 1 기본 구현 commit 2 UT 추가 commit 3 리뷰 의견 수정 commit 4 예외 처리 보강 │ └── 같은 PR에 계속 반영 ↓ Review 완료 ↓ Merge ↓ pilot

P4에서 같은 CL을 계속 수정하고 Shelve를 갱신하면서 리뷰받는 흐름과 사고방식이 비슷합니다.

6. 가장 많이 헷갈리는 것: Git Stash

P4 Shelve

서버 공유용

변경을 서버에 보관하고 다른 사람과 공유하거나 리뷰에 사용할 수 있습니다.

Git Stash

내 PC 임시 보관용

작업 중인 변경을 잠깐 치워두는 용도입니다. 일반적으로 리뷰나 공유를 위한 기능이 아닙니다.

주의: 이름 때문에 git stash를 P4 Shelve와 동일하게 생각하기 쉽지만, 실제 실무 목적은 다릅니다.

7. 실제 Pilot Branch 작업을 예로 보면

pilot │ └── feature/JIRA-1234-tx-refactoring │ ├─ 코드 수정 ├─ commit ├─ push │ └─ Pull Request │ ├─ base : pilot ├─ review ├─ 수정 → commit → push ├─ approval └─ merge ↓ pilot
P4 관점 번역:
Feature branch에서 Commit + Push한 상태를 “Shelve 해둔 상태”처럼 생각하고, PR 리뷰가 끝나서 Merge되는 순간을 “Submit”에 가깝게 생각하면 이해하기 쉽습니다.

8. 초보자용 4단계 기억법

1. Commit

내 PC에 변경 이력을 남긴다.

Local
2. Push

내 branch를 GitHub 서버에 올린다.

Remote
3. PR

“이 변경을 pilot에 넣어 주세요”라고 리뷰 요청한다.

Review
4. Merge

승인된 변경을 pilot/main 같은 공식 branch에 반영한다.

Official Branch

동료에게 공유할 핵심 문장

P4 Shelve ≈ Git Feature Branch의 Commit + Push

P4 Submit ≈ GitHub Pull Request Merge

Commit만 하면 아직 내 PC에만 있을 수 있고, Push해야 GitHub 서버에 올라갑니다. Git Stash는 Shelve가 아니라 로컬 임시 보관 기능에 가깝습니다.
