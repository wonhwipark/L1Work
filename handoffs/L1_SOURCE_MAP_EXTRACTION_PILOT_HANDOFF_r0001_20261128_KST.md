## 2. G0 및 P0 구축 절차

1. **G0-1부터 시작.** r0005에 따라 실제 Updater·Analyzer·Qwen 실행 진입점과 지문을 확인해요. 기존 G0 root·권한·분모·예산 조건을 적용해요. Discovery 7건의 revision과 범위를 대조하고 legacy 121개와 분류 합계 120개의 차집합을 파일 단위로 정산해요.
2. **추출 가능성을 확인.** `NR L1 Tx → UL Tx Switching`에서 주 빌드 A를 고정해요. 분기 대조용 실제 빌드 B는 별도 stream으로 지정해요. 현재 Analyzer가 A에서 해석된 호출 대상, 선택된 include, 메시지 ID와 등록/전달 근거를 실제로 반환하는지 작은 표본으로 확인해요. 생성 입력은 생산자 기록에서 분석 대상 build의 입력 revision·지문과 해당 산출물 해시를 대조할 수 있는지 확인해요. 확인 불가 시 해당 TU·유형과 사유, 필요한 읽기 전용 확인을 반환해요.
3. **원인 재현과 기준표 확정.** 기존 Map에서 지적된 관계 한 건을 원문과 대조해 차이가 처음 나타난 지점이 입력 revision/빌드, 추출, 심볼 결합, 조회 중 어디인지 기록해요. 각 대상 유형별로 실제 양성과 반례를 원문에서 선정하고, 기대 관계·방향·검증 상태·필수 근거 및 고정 분모를 남겨요. 예비 측정 사례와 정식 수락 사례는 분리해요.
4. **TU별 추출 후 결합.** 저장소·소스 snapshot·빌드 지문·분석기 지문을 고정하고 원본 파일, 생성 파일, 제외 사유를 구별해요. 심볼은 동일 빌드에서 해석된 안정 ID를 우선 사용해요. 대체 ID는 qualified name·시그니처·한정자·정의 범위·linkage와 확인된 템플릿 특수화/인스턴스를 포함해요. 내부 linkage는 TU도 구별해요. 대체 ID는 선언·정의 식별을 돕고, 호출 대상 확정에는 호출 지점의 해석 증거가 필요해요. 동일 관계도 조건이나 적용 TU 범위가 다르면 조회 레코드를 나눠요. 대표 anchor로 묶을 때는 조건·범위가 동일함을 입증하고 지점 수와 대표 여부를 기존 메타에 표시해요. 이를 표현할 수 없으면 anchor별 레코드를 사용해요. r0005의 완전한 레코드 절단과 `truncated=true` 및 누락 표시를 적용해요.
5. **격리 결과 대조.** 파일·생성 헤더·빌드 인자·등록표 변경에 대해 이전/새 역의존 합집합을 사용해요. 삭제·이름 변경으로 사라진 관계와 역참조는 새 세대에서 철회해요. 실제 저장 지문·경합·Reader readback은 r0005의 기존 검증과 승인 범위에서 확인해요.

## 3. Updater의 결정형 관계 검증

공통 검사 순서는 **허용 범위와 고정 지문 → 원문 anchor 해석 → 심볼/키·방향 대조 → 관계별 근거 충족 → 충돌 검사**예요. 검증 경로는 같은 입력에서 같은 결과를 내야 해요. 각 근거는 소스 snapshot·build·상대 경로·심볼/줄 범위·추출 방법·근거가 입증하는 명제를 가리켜요. Qwen이 반환한 ID와 위치는 고정 입력의 근거 목록에 대조한 뒤 검사에 사용해요. 모델이 생성한 확정 문구나 상태 값은 검증 상태 쓰기에 사용하지 않아요.

| P0 관계 | `VERIFIED`에 필요한 조건 | 근거가 모자랄 때 |
|---|---|---|
| 파일/모듈 포함·include | 권한 있는 파일 목록에 경로와 모듈 소속이 확인됨. include 관계는 TU가 실제로 해석한 대상 경로와 지시문 위치가 일치함 | 동명 헤더, include 순서나 생성 경로 미해소는 후보 |
| 선언·정의·포함 | 심볼 정체성·선언/정의 위치·linkage 일치. TU 종속 심볼과 해석이 달라지는 템플릿 인스턴스 구별 | 정체성이 불명확하면 결합 보류 |
| 직접 호출 | 호출자와 호출 위치, 동일 빌드에서 해석된 피호출 선언과 가용한 정의가 일치함 | 외부 심볼의 선언만 입증되면 해당 선언에 대한 호출 명제만 검증하고 정의 결측 기록. 미해소 overload·가상 호출·함수 포인터는 대상 후보 |
| IPC·메시지·payload | r0003의 `sends`/`receives`/`payload` 방향에 맞는 각 endpoint anchor와 API 계약을 확인. 송수신을 연결할 때 빌드·인터페이스·방향·정규 ID와 필요한 payload 타입 대조. 상수식·별칭은 같은 빌드에서 전개·평가한 값으로 비교 | 정규 ID 평가 불가 또는 계약·payload 미해소는 해당 명제 보류. 동번호라도 별개 인터페이스는 연결 차단 |
| Handler 등록·dispatch | `registers`는 초기화 시점의 정적 등록에서 슬롯·키·Handler를 확인. `dispatches`는 lookup 또는 switch에서 해당 키의 실제 전달 위치와 대상을 확인. P0 범위에서 같은 슬롯·키의 복수 등록/쓰기 지점을 먼저 탐색 | 복수 등록/쓰기 지점이면 `CONFLICT`로 남기고 단일 유효 대상 확정 0건. 탐색 근거 부족 시 미검증. 런타임 유효 대상의 판정은 별도 P1 질문 |
| 빌드 활성 조건 | 분기 anchor·중첩 및 선행 형제 분기 배제 조건·실제 플래그/설정 헤더·target·생성물 지문이 해당 TU와 일치함 | 생성 입력이 오래됐거나 생산자 기록과 해시를 연결할 수 없으면 의존 관계의 활성 여부와 확정 보류. 런타임 guard는 별도 명제 |

저장 필드는 기존 r0003/r0005에 매핑해요. `EXTRACTED/INFERRED/UNKNOWN`은 추출 상태이며, `VERIFIED/UNVERIFIED/CONFLICT`는 검증 상태예요. 같은 조건에서 근거가 충돌하면 `CONFLICT`로 기록해요. 단순 출현처럼 좁은 명제만 입증됐으면 그 명제와 미확인 관계를 구분해요. 현재 pin과 불일치하는 생성 입력이나 다른 빌드 관계는 정확한 anchor가 있어도 현재 빌드의 확정 관계로 승격되지 않아요.

## 4. P0 수락 게이트 → r0005 소비 비교

**수락 분모는 사전 봉인한 원문 정답표의 양성 관계 수예요.** 유형별 확정률은 ‘정확한 방향·지문·원문 근거로 VERIFIED된 양성 수 ÷ 해당 유형 전체 양성 수’로 계산해요. 후보·UNKNOWN·검색 실패·미처리 양성도 분모에 남겨요. 중복 anchor 여러 개로 분자를 늘리지 않아요. 유형별 양성·반례는 각각 최소 1건을 포함하고, 실제 표본이 작으면 오탐·누락 원인을 확인하는 초기 pilot 범위로만 판정해요. 유형별 수락 하한 수치는 별도 대표 모듈 표본에서 한 번 예비 측정한 뒤 업무 GPT가 근거와 함께 제안해요. 정식 시험 전에 사용자와 합의하고 양성·반례 목록, digest, 하한을 고정해요. 정식 결과를 본 뒤 분모나 하한을 수정해야 하면 새로운 표본과 시험 revision이 필요해요.

| 상태 | 판정 및 이동 |
|---|---|
| PASS | 대상 유형마다 올바른 확정 ≥1건, 사전 하한 충족, 잘못된 확정·빌드 혼합 각 0건, 필수 반례 통과, TU 순서를 바꾼 재실행에서 논리 관계·근거 집합 일치. 격리된 A snapshot을 고정하고 r0005 소비 비교로 이동 |
| FAIL | 전부 UNKNOWN, 유형별 하한 미달, 잘못된 확정, 필수 반례 실패 또는 비결정성. 소비 비교를 중단하고 실패 유형의 근거 수집·해석·검증 중 최초 결손을 보완한 뒤 같은 계약에서 재시험 |
| HOLD / 업무 미검증 | 활성본·필수 입력 지문·정답표·하한 미확정은 HOLD. 실제 B가 없으면 합성 분기는 로직 회귀용으로만 인정하고 빌드 분기 유형은 업무 미검증으로 기록. 별도 범위로 합의한 경우에만 그 유형을 제외한 축소 비교를 허용하며, D1/D3 입력·보고서에도 제외 범위 명시 |

M-D0~M-D3는 **사전에 지정한 주 빌드 A의 같은 source/build로만** 비교해요. B는 분기 대조 전용이에요. 정식 비교에는 별도 holdout을 사용하고 안전선과 D3−D2 판정은 [r0005 실행 참조서 §5](https://github.com/wonhwipark/L1Work/blob/7a55251975e7dddb557c7f69f7261101e3654817/handoffs/L1_KNOWLEDGE_UPDATER_QWEN36_EXECUTION_REFERENCE_r0005_20261128_KST.md)를 적용해요. 최초 구축·증분 비용과 질문별 소비 비용을 각각 계측해요.

## 5. 업무 GPT에서 바로 사용할 요청문
