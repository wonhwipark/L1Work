9. Git Fetch · Merge · Rebase를 그림으로 이해하기

서버의 최신 상태를 가져오는 것과 그 변경을 현재 branch에 합치는 것은 서로 다른 동작입니다. 8장의 Merge 두 방향 중 여기의 merge는 ② 로컬 merge입니다.

git fetch upstream

서버 상태만 갱신

upstream의 최신 commit 정보를 로컬 repository로 가져옵니다. 현재 작업 파일은 바꾸지 않습니다.

Before upstream/smp1900 → A─B
↓ fetch
After upstream/smp1900 → A─B─C
git merge upstream/smp1900

base를 현재 CL branch에 합침

현재 CL_987654에 최신 smp1900 변경을 합칩니다. 양쪽이 같은 부분을 바꿨다면 conflict가 발생합니다.

Before base A──B──C \ CL └──X After base A──B──C \ \ CL └──X──M M의 부모 = X와 C
git rebase upstream/smp1900

내 commit을 최신 base 위로 다시 쌓음

CL_987654의 commit을 최신 base 뒤에 다시 적용합니다. 기존 commit의 SHA가 바뀝니다.

Before A──B──X base A──B──C rebase 후 A──B──C──X′ X → X′ : 새 SHA
Rebase / force push 주의: 이미 공유된 branch를 rebase하면 commit SHA가 바뀌며, 원격 branch 갱신에 force push가 필요할 수 있습니다. 다른 사람이 사용하는 branch나 자동화가 만든 기존 Open PR branch에서는 기본 동작으로 사용하지 않습니다.
pull은 언제 쓰나? 일상적인 개인 작업에서는 git pull을 사용할 수 있습니다. 다만 Part B의 스킬은 각 단계와 대상 branch를 검증해야 하므로 fetch와 merge를 분리합니다.

10-1. Git Worktree: Branch 전환과 별도 작업 폴더의 차이

Branch는 코드 이력의 갈래이고, Worktree는 특정 branch의 파일을 실제로 펼쳐 놓은 작업 폴더입니다. 일반 Git 사용자는 한 폴더에서 branch를 바꾸지만, git worktree를 사용하면 하나의 로컬 repository에 여러 작업 폴더를 연결할 수 있습니다.

단일 폴더 = Switch로 전환Worktree = 폴더별 동시 작업

Worktree, Branch, Clone을 구별하면

구분BranchGit Worktree별도 Clone
무엇인가?Commit 이력을 가리키는 참조한 로컬 repository에 연결된 독립 작업 폴더별도의 로컬 repository 사본
실제 작업 파일Branch만 만들어서는 새 폴더가 생기지 않음Worktree마다 별도 파일과 Staging 영역Clone마다 별도 파일
Git 객체 / 이력같은 repository 안에서 공유기본 repository와 공유일반적으로 별도 객체 저장소
디스크 사용추가 파일 폴더 없음새 작업 파일과 빌드 결과만큼 증가Git 객체까지 별도로 저장할 수 있음
P4 사용자 관점: 여러 Git Worktree는 P4에서 별도 Workspace를 여러 개 두는 모습과 일부 비슷합니다. 다만 Git Worktree들은 동일한 로컬 Git repository의 이력과 참조를 공유한다는 점에서 완전히 같지는 않습니다.
현재 팀 운영 기준: 기본 작업 위치는 /home/whpark/Project/smp1900 하나이며, 새 Worktree 자동 생성은 하지 않습니다. 여러 작업을 진행할 때도 기존 변경을 먼저 보호하고 같은 폴더에서 local branch를 전환합니다. Git은 일반적으로 동일한 local branch를 두 Worktree에 동시에 체크아웃하지 못하게 합니다.

연결된 경로, branch, 상태를 확인합니다. 이 명령은 제거하지 않습니다.

삭제는 별도 승인

11. Merge와 Rebase 차이

8장의 구분에 따라 여기의 Merge는 base → 내 branch 로컬 통합입니다.

MERGE · Part B 기본 방식

기존 commit을 유지하면서 두 이력을 연결

base A──B──C \ \ CL └──X──M M의 첫 번째 부모 = X M의 두 번째 부모 = C 기존 X는 사라지지 않음

Merge commit M이 X와 C를 모두 부모로 가지므로 기존 CL commit X의 이력을 유지합니다.

VS
REBASE · Part B 기본 사용 안 함

내 commit을 새 base 위에 다시 작성

Before base A──B──C CL A──B──X After base/CL A──B──C──X′ 기존 X → 새로운 X′ SHA 변경

기존 X가 그대로 이동하는 것이 아니라 같은 변경을 기반으로 새 commit X′가 만들어집니다.

자동화가 이미 만든 upstream Open PR에서 conflict를 해결하고 같은 branch로 push하는 운영 흐름입니다.

14. 자동화가 먼저 만든 Open PR에서 시작한다

일반 개발의 Fork 흐름과 달리 이 스킬은 이미 회사 upstream 안에 존재하는 자동화 branch와 Open PR을 이어받습니다.

자동화 시스템이 먼저 수행 P4 SMP1800 CL_987654 ↓ 자동 반영 시도 회사 upstream의 CL_987654 branch 생성 ↓ Open PR 생성 (base = smp1900) ↓ Conflict 발생 ↓ 담당자에게 PR URL + upstream/CL_987654 전달 ↓ ★ 여기부터 l1-cl2git-merge ★
일반 Fork 개발과 구분: 일반 개발은 보통 개인 Fork(origin)에 작업 branch를 push하고 upstream으로 PR을 보냅니다. 반면 이 conflict 복구 스킬은 자동화가 만든 기존 upstream branch 자체를 사용합니다. 자세한 차이는 부록 A를 참조하세요.

15. 정본: l1-cl2git-merge 6단계 흐름

이 문서에서 스킬의 6단계 정의는 이 절 하나만 정본입니다. 다른 절은 이 흐름을 반복하지 않고 여기만 참조합니다.

1로컬 상태 점검현재 repo/branch, 수정 파일, 진행 중 Git 작업, 사용자 변경 보호 여부 확인.
2PR / CL 검증PR=OPEN, head=CL_987654, base=smp1900, 회사 upstream인지 확인하고 CL ID·P4 CL 근거를 확보.
3Fetch + branch 준비upstream 최신 정보 갱신 후 exact CL branch를 local tracking branch로 준비.
4Base Mergeupstream/smp1900을 local CL_987654에 merge.
5CL 의도 보존 확인Conflict가 있으면 해결하고, 없어도 CASE F 누락 검사를 수행한 뒤 정적 검증.
6Commit + 보호 검증 + Push등록된 source_code Repo, upstream 예외, OPEN PR과 정확한 CL branch를 Push 직전 검증한 뒤 같은 branch로 Push, 기존 PR 갱신.
STEP 4 Base Merge 완료 ↓ conflict 발생? ├─ YES → conflict 해결 ──────┐ └─ NO ───────────────────────┤ ↓ CASE F: CL 의도 누락 검사 ├─ 누락 있음 → 보완/분석 └─ 누락 없음 ↓ 정적 검증 ↓ STEP 6 Commit + Push ↓ 기존 Open PR 갱신
8장의 Merge 구분을 적용하세요. STEP 4는 “base → 내 CL branch”의 로컬 git merge입니다. 최종 PR Merge는 스킬 범위 밖이며 사용자가 GitHub에서 수행합니다.
왜 pull 대신 fetch + merge인가? 일상 작업에서는 pull을 사용할 수 있지만, 이 스킬은 PR·remote·branch와 각 단계 결과를 검증해야 하므로 fetch와 merge를 분리합니다.

17. 상황별로 스킬은 어떻게 행동하나?

CASE A

로컬에 수정 중인 파일이 있음

사용자 작업을 삭제하지 않습니다. 안전하게 보존할 수 있으면 스킬의 안전한 보존 방식으로 보호하고, 불가능하면 사용자에게 확인 후 중단합니다.

금지: 임의의 reset --hard, clean -fd
CASE B

같은 local CL branch가 이미 있음

로컬에만 있는 commit이 있는지 먼저 확인합니다. 고유한 미Push commit이 있으면 강제로 지우거나 덮어쓰지 않습니다.

안전할 때만 오래된 local branch를 정리
CASE C

PR / branch 정보가 맞지 않음

PR이 OPEN이 아니거나 base/head/upstream 조건이 다르면 진행하지 않습니다.

BLOCKED: 임의로 새 branch나 새 PR을 만들어 우회하지 않음
CASE D

단순 Conflict

라인 이동, include 위치 변경, 명확한 rename/move처럼 CL 의도가 분명한 경우 동일 branch에서 해결합니다.

분류: SAFE_CONFLICT
CASE E

의미적 Conflict

API/signature, class 위치, ownership/control flow 변화 등 텍스트 선택만으로 CL 의도를 보존하기 어려우면 코드 분석이 필요합니다.

code-analyzer → 필요 시 knowledge → code-fix
CASE F

Conflict 표시는 없지만 CL 일부가 빠짐

Git conflict가 없다는 이유만으로 성공 처리하지 않습니다. P4 CL 의도가 target 코드에 모두 대응됐는지 확인합니다.

INCOMPLETE_PORT → 누락 해결 후 push
중요: CASE F는 conflict가 발생한 경우뿐 아니라 발생하지 않은 경우에도 15장 STEP 5에서 반드시 확인합니다.

하나의 Git repository에 연결된 독립 작업 폴더. 기본 Worktree 외에 보조(Linked) Worktree를 둘 수 있고, Git 객체와 Branch 참조는 공유하지만 파일·Index·HEAD는 각자 가집니다. 10-1장 그림 참조.

원격 branch 이력을 일반적인 fast-forward 규칙을 무시하고 갱신하는 push 방식. 공유 branch에서는 이력 충돌 위험이 있어 주의가 필요합니다.

25. CL2Git의 특수한 upstream Push는 어떻게 보호하나?

일반 개발 Push와 다릅니다. l1-cl2git-merge는 신규 PR을 만드는 스킬이 아니라, 자동화가 이미 만들어 놓은 같은 회사 upstream Repo의 기존 Open PR과 CL branch를 복구합니다.

일반 개발: 내 origin(Fork) → PRsource_code의 등록된 Fork URL과 일치해야 함
↕ 작업 방식 구분
CL2Git 복구: 기존 upstream/CL_987654 → 기존 PR 갱신Push 이전에 아래 4가지 별도 조건 전부 확인
① 등록된 source_code

현재 PC의 코드 Repo가 정확히 등록되어 있고 실제 upstream Push URL이 사용자가 승인한 공식 URL과 같아야 합니다.

② 제한된 예외 승인

repo-config allow-cl2git로 정확한 upstream URL의 push_exceptions.cl2git를 따로 등록해야 합니다. 일반 upstream Push까지 허용되는 것은 아닙니다.

③ PR 검증

신뢰할 수 있는 provider에서 새로 조회한 PR 증거로 OPEN, base=smp1900, PR head Repo=같은 upstream Repo를 확인합니다.

④ Branch 일치

PR head가 CL_숫자 형식이고, 실제 로컬 현재 branch도 같은 CL 번호여야 합니다. 다른 branch로 Push하지 않습니다.

실패 시: push-preflight에서 BLOCKED. 스킬이 멋대로 개인 Fork나 다른 upstream branch에 재Push하거나 PR을 새로 만들지 않습니다. Push 대상만 안전해도 conflict 해결·CL mapping 정적 검증이 실패했다면 Push하지 않습니다.
Skillsilent 미설치 동료도 동일 정책: l1-github가 설치되어 있으면 해당 경로를 우선 사용하고, 없으면 l1-cl2git-merge에 포함된 Token Fallback Push Guard가 Canonical JSON을 검사합니다. Mango MCP 경로 역시 사전검증이 필수인 운영 계약으로 사용합니다. 관련 흐름은 Part B 15장 참조.

동료의 작업 = 부모 PR (예: #4199)

부모 작업 P1 · P2 · P3

아직 Merge되지 않았던 시점에 내 작업이 이 브랜치를 기반으로 시작했습니다.

P1P2P3부모 PR
내 작업 = 자식 PR (예: #4200)

부모 위에 내 커밋 6개 추가

내 브랜치에는 부모 커밋뿐 아니라 내 C1~C6까지 이어져 있습니다.

부모 P1~P3→내 C1~C6
예시는 구조 이해용입니다. 부모 PR #4199, 자식 PR #4200은 이해를 위한 예시 식별자입니다. 앞서 공유한 사례의 “우리 6개 커밋·8개 파일”은 설명에 반영했지만, 실제 부모/자식 PR 링크와 변경 파일 수는 실행 시 조회·검증합니다.

29. 3단계 그림으로 이해하기 — 단계를 눌러보세요

왜 예전 부모 커밋이 자식 PR에 남아 있을까?

STEP 1

동료 PR 위에서 내 개발을 시작

부모 PR은 아직 Open입니다. 내 브랜치가 부모 커밋 P1~P3를 공유하고, 그 뒤로 내 작업 C1~C6가 추가됐습니다.

공식 dev아직 부모 미반영
D0
부모 PR동료 Open PR
D0→P1→P2→P3
자식 PR내 작업 브랜치
D0→P1P2P3→C1C2C3C4C5C6
이 상태는 Stacked PR의 자연스러운 구조입니다. 부모 PR이 Merge되기 전에는 내 브랜치가 부모 작업을 포함합니다.
STEP 2 · 문제

부모 PR이 Squash Merge돼도 내 브랜치의 예전 이력은 그대로

GitHub가 부모 커밋 P1~P3을 한 커밋 S로 합쳐 dev에 반영했습니다. 하지만 내 브랜치는 여전히 P1~P3을 포함합니다.

최신 dev부모 작업 반영
D0→SSquash 1개
자식 PR정리 전
D0→P1P2P3→C1C2C3C4C5C6
문제 원인: S는 부모 커밋 P1~P3을 그대로 보존한 것이 아니라 새 커밋입니다. Git의 공통 조상(merge-base)이 자동으로 S로 바뀌지 않으므로 자식 PR의 Files changed에 부모 변경까지 섞여 보일 수 있습니다.
STEP 3 · 해결

최신 dev 위로 내 커밋 6개만 이동

stacked-pr-cleanup이 부모 P1~P3은 재적용하지 않고, 부모 PR Head 뒤의 내 커밋 C1~C6만 최신 dev 위에 다시 적용합니다.

최신 devSquash 반영 완료
D0→S
정리된 자식 PR최신 dev 기준
D0→S→C1′C2′C3′C4′C5′C6′
결과: 부모 작업은 dev의 Squash 커밋 S에만 반영되어 있고, PR에는 내 작업의 변경만 남는 것이 목표입니다. C1′~C6′의 SHA는 기존 C1~C6과 다르므로 실제 Push 전에 승인이 필요합니다.
D0 = 공통 시작점P = 부모 작업C = 내 작업S = Squash Commit

그림은 이해를 위한 단순화입니다. 실제 커밋 수와 PR 관계는 GitHub의 HEAD·merge SHA로 다시 확인합니다. 버튼은 설명만 바꾸며 Git 명령이나 Push는 실행하지 않습니다.

왜 일반 Merge와 다를까? 부모 PR을 일반 Merge Commit으로 합쳤다면 원래 부모 커밋의 조상 관계가 보존될 수 있습니다. Squash Merge는 새로운 커밋 S만 남기므로 자식 브랜치를 재정렬할 필요가 생깁니다.

→

31. stacked-pr-cleanup이 실제로 하는 일

명령을 한 번에 무조건 Push하는 기능이 아닙니다. 준비 → 검증 → 원본 게시의 3단계로 나뉩니다. 각 단계 사이에 안전 경계가 있습니다.

① PREPARE

기존 PR 보존하며 정리 준비

부모 MERGED / 자식 OPEN 여부와 같은 Repo 관계 확인 → Preview → 사용자 준비 승인 → 로컬 임시 브랜치에서 내 커밋만 Rebase

원격 PR 아직 변경 없음
② VERIFY

부모 변경이 빠졌는지 검사

예상 자식 파일 목록과 실제 Diff 비교, 커밋 수, 조상 관계, git diff --check 검사

Diff 불일치 시 중단
③ PUBLISH

승인 후 기존 PR 갱신

별도 사용자 승인 → 원격 SHA / GitHub PR 상태 / Push URL 재검증 → --force-with-lease로 안전 갱신

동료 추가 Push 감지 시 중단
내 PC 사용 방식은 기존과 동일: /home/whpark/Project/smp1900 기본 폴더 하나에서 임시 브랜치를 사용합니다. 추가 Worktree 폴더를 생성하지 않습니다. 기존 작업 파일이 남아 있거나 임시 브랜치가 충돌하면 강제로 삭제하지 않고 중단합니다.
기술적으로는 어떤 Git 작업인가요? (필요할 때만 펼치기)

핵심 명령 개념:

git rebase --onto <최신-dev-tip> <부모-PR-head-SHA> <자식-PR-head>

--onto는 재배치 목적지입니다. 부모 HEAD 다음부터 자식 HEAD까지의 커밋을 새 Base 위로 옮깁니다. 실제 v0.3.44는 보호 로직이 있으므로, 직접 Git 명령을 실행하기보다 스킬을 사용해야 합니다.

주의: 부모 변경이 최신 dev에 포함되지 않았거나, 자식 범위에 Merge Commit이 섞였거나, Conflict가 발생하면 자동 완료하지 않습니다.

32. 안전장치 — 왜 Push에 별도 승인이 필요한가?

준비 단계 · 원격 변경 없음

기존 Open PR은 그대로 둠

임시 로컬 브랜치에서 Rebase·검증합니다. 스킬이 준비를 완료했다고 곧바로 회사 GitHub의 동료 브랜치를 덮어쓰지 않습니다.

게시 단계 · 명시 승인 필수

동료 변경이 생겼으면 중단

이력 재작성은 새 SHA를 만들기 때문에 --force-with-lease가 필요합니다. 실행 직전 원격 HEAD가 예상 SHA에서 달라지면 Push하지 않습니다.

검증 완료 + 사용자 게시 승인원본 PR을 수정해도 되는지 별도 확인
↓
현재 OPEN PR · Base · 원격 Repo URL 재조회승인된 저장소만 허용; upstream은 allow-stacked-pr 예외 별도 필요
↓
원격 HEAD SHA가 처음 확인한 값과 같은가?예: 동료가 새 Commit을 Push했다면 값이 달라짐
↓
일치할 때만 exact --force-with-lease Push기존 Open PR 갱신 · 새 PR 생성하지 않음
보호 기능의 범위: force push를 일반적으로 허용하는 것이 아닙니다. 사용자가 승인한 정확한 자식 PR의 특정 이전 SHA만 조건부 갱신합니다. 원자적 lease를 제공하지 못하는 Mango MCP 경로에서는 게시 단계가 차단됩니다.

34. 실제로 스킬에 어떻게 요청하나?

자연어 요청 예시

“부모 PR #4199는 Squash Merge됐고, 자식 Open PR #4200에 부모 작업까지 Diff가 남아 있어. l1-github stacked-pr-cleanup으로 우리 작업 커밋만 최신 dev 위에 정리해줘. 먼저 Preview와 정리 후 파일 목록을 보여주고, 원본 Push는 승인받은 뒤 진행해줘.”

필요한 입력: 실제 부모 Merged PR URL과 자식 Open PR URL 두 개. 번호만 제공할 경우 저장소 정보가 불명확하면 URL 확인이 필요합니다. 성공 후에는 GitHub의 Files changed와 CI 상태를 최종 확인합니다.
스킬 CLI 명령 순서 보기 (고급 사용자용)
# 1) Preview · 원격 PR 불변
python scripts/l1_github.py stacked-pr-cleanup \
  --parent-pr '<MERGED_PARENT_PR_URL>' \
  --child-pr '<OPEN_CHILD_PR_URL>'

부록 A

Fork · Clone · origin · upstream

일반 개발의 Fork 모델과 l1-cl2git-merge의 예외적 upstream 직접 작업을 분리해서 봅니다.

A-1. 일반 개발: SMP1900을 Fork해서 사용

팀의 일반 개발 흐름에서는 회사 원본 repository인 SMP1900을 개인 계정으로 Fork해 사용합니다. l1-github fork-setup 기준 역할은 아래와 같습니다.

upstream

회사 원본 / canonical repository

base 시작 기준, 최신 base 가져오기, PR target 역할입니다.

upstream ↓ 회사 SMP1900
VS
origin

내 Fork

일반 feature/fix branch를 push하는 개인 작업 repository입니다.

origin ↓ 내 Fork of SMP1900
[회사 GitHub] upstream = SMP1900 │ │ Fork ▼ [내 GitHub] origin = 내 SMP1900 Fork │ │ clone / feature 작업 / push ▼ [내 PC] local feature branch │ └──── PR ────► upstream/smp1900
remote 이름은 Git이 강제하는 고정어가 아닙니다. 다만 팀의 l1-github fork-setup은 upstream = 회사 원본, origin = 개인 Fork 역할로 구성합니다.

A-2. l1-cl2git-merge는 일반 Fork 작업과 다르다

자동화 conflict 복구에서는 이미 회사 upstream repository 안에 CL_987654 branch와 Open PR이 존재합니다. 따라서 개인 Fork에 새 branch를 만들지 않습니다.

[회사 upstream SMP1900] upstream/smp1900 │ └── 자동화 생성 ──► upstream/CL_987654 │ ├─ 기존 Open PR │ └─ 담당자가 같은 branch 이어받음 ↓ conflict 해결 / commit ↓ upstream/CL_987654 push ↓ 기존 Open PR 갱신 ※ 새 개인 Fork branch / 새 PR을 만들지 않음
Part B 전제(v0.3.5): 우선 l1-github를 사용하지만, 미설치 시에도 Token Fallback의 독립 Push Guard가 동일한 canonical 설정을 검사합니다. 제공된 PR은 OPEN / 같은 upstream Repo / base=smp1900 / head=CL_987654 조건을 만족해야 하며, upstream 예외 설정도 필요합니다. 25장 참조.
