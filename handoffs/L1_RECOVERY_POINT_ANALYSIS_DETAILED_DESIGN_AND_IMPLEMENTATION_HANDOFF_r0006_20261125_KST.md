## 2. 코드 폴더 사전 확인

**분석 대상은 업무 호스트의 제품 소스 폴더예요.** 업무 GPT가 다음 분기를 설계하고, 실행 호스트의 Qwen 또는 허용된 로컬 Agent가 읽기 전용으로 확인해요. GitHub 인계 문서의 위치, 스킬 설치 폴더, 결과를 저장하는 Workspace는 각각 용도가 달라요.

| 실행 때 확인한 상황 | 동작 |
|---|---|
| 이번 요청에 제품 소스 경로가 있음 | 지정 경로의 존재·읽기 권한·대상 프로젝트를 먼저 확인해요. 읽을 수 없거나 프로젝트가 다르면 이유와 함께 올바른 경로를 한 번 물어요. 저장된 다른 경로로 자동 전환하지 않아요. 경로·프로젝트가 유효하면 아래 revision 분기로 이어가요. |
| 경로 미지정, 같은 호스트·프로젝트에 유효한 저장 경로가 하나 있음 | 저장 경로를 검증하고 **경로 재질문 없이 재사용**해요. 아래 revision 분기로 이어가요. |
| 경로 기록 없음, 이동·권한 문제, 다른 저장소, 복수의 유효 후보 | 확인 가능한 원인이나 후보만 제시하고 **“이번에 분석할 제품 소스 폴더 경로가 어디인가요?”**라고 한 번 물어요. 여러 후보면 확인된 경로 중 하나를 고를 수 있게 해요. |
| 경로·프로젝트 유효, 요청 revision과 관찰 revision 일치 | 기존 조회 범위와 지정 revision을 고정하고 질문 없이 분석해요. |
| 경로·프로젝트 유효, 요청 revision과 관찰 revision 불일치 | 두 revision과 불일치 이유를 제시하고 **“이번 분석에 어느 revision을 사용할까요?”**라고 한 번 물어요. 현재 경로 재입력을 요구하지 않아요. 사용자가 선택한 revision을 해당 호스트에서 읽을 수 있는지 확인한 뒤 고정해요. |
| 유효한 경로, 요청 revision 미지정 | 이번 실행에서 관찰한 Git branch/commit 또는 P4 stream·파일 revision을 고정해요. 같은 경로에서 HEAD가 바뀌면 질문 없이 새 revision의 영향을 받는 기존 근거를 갱신해요. |
| 사용자가 답함 | 경로 또는 선택 revision을 검증해요. 둘 다 유효할 때 분석을 시작하고 허용된 기존 기록에 저장해요. 이번 요청 전용 값은 그 범위에만 기록해요. 응답이 유효하지 않거나 아직 해결되지 않은 조건이 있으면 구체적 사유와 확인 대기·재개 위치를 남겨요. 사용자가 값을 바로잡으면 필요한 분기에서 재개해요. |
| 응답을 받을 수 없는 무인 실행 | 확인할 경로/revision, 필요한 선택과 이유를 기존 Work에 남겨요. 확보한 Seed 정보는 보존하고 입력 검증 뒤에 분석을 재개해요. |

Git이면 요청한 디렉터리와 실제 저장소 루트·상대 범위, 현재 branch 또는 고정 commit을 대조해요. P4이면 기존에 허용된 client/view의 로컬 매핑과 대상 stream/depot 범위를 확인해요. Git 메타데이터가 없는 정식 소스 스냅샷은 기존 릴리스 식별 근거를 사용해요. 경로·프로젝트 확인 후 지정 revision의 일치 여부를 별도로 확인해요. 경로와 revision을 함께 확인해야 하는 경우 현재 알 수 있는 선택 조건을 한 번의 질문에 묶어요. 최초 입력 확인에서 사용자 질문은 최대 1회예요. 답변 뒤에도 입력 고정이 안 되면 질문을 반복하지 않고 대기 상태와 재개 위치를 기록해요. 입력 고정이 완료되기 전에는 제품 소스 분석을 시작하지 않아요. 임의의 현재 디렉터리 선택·디스크 전체 탐색·자동 checkout은 하지 않아요. 실제 경로와 고정 revision은 업무 Work에 보존해요.

### 첫 사례의 분석 범위와 OpenCode 확인

- **대상 분모(A2).** 지식 분석의 1차 담당 범위는 NR BCH, NR L1 Tx, LTE ChCfg, LTE L1 Tx예요. 215행(P120/F95)은 분류 검토 후보이고 Layer1 약 2천 파일은 구술 추정치예요. 실제 파일·모듈 대응, Seed가 속한 업무 범위, 선택한 파일과 조사할 후보 수는 따로 기록해요. Recovery는 Seed의 소유자 경로를 따라가며, 같은 원인 규칙을 판정하는 데 필요한 공통 코드·HAL·PHY·IPC 경계도 근거를 적고 포함해요.
- **사례 선택.** 기존 Recovery Work의 유효한 비-timeout Seed 하나를 사용해요. 기존 NR L1 Tx → UL Tx Switching 결과는 해당 Seed의 원인·revision·build·경로에 맞을 때 재사용해요. 다른 Seed는 그 Seed에서 보호의 적시성과 첫 위반을 가르는 경로로 시험해요. 지식 후보를 연결할 때는 기존 Module → Feature → Scenario 분류와 Procedure 교차 탐색을 사용해요.
- **실행 환경(D2).** `.claude/skills`에서 발견한 이름, 실제 실행 파일·버전, 지원 action·입출력·권한 및 기존 영수증을 대조해요. OpenCode v1/v2 worker와 `parallel-extract-plan`·`parallel-extract-check`는 설치본에 있을 때 확인할 항목이에요. 첫 사례는 짧은 단계표와 명시적인 action 호출로 수행해요. 도구 이름이 해석되는지와 실제 성공 영수증이 남는지를 구별하고, 도구 누락 시 그 단계의 차단·재개점을 기록해요. 기존 helper의 `may_invoke_doc_converter=false`와 게시 제한은 코드에서 보존하고, Converter는 5절의 지원 경로로 호출해요.

## 3. 현행 스킬을 Qwen 구현 지침으로 바꾸는 순서

업무 GPT는 기존 스킬 원문·지원 action·기존 Work 표본을 대조해, 단계마다 **현재 담당 기능 / 확인한 입력과 출력 / 변경이 필요한 지점 / 통과할 시험**을 적어요. 로컬 Agent가 확인할 수 없는 설치 정보는 미확인으로 남겨요. 아래 V0~V6는 분석 순서이고, 설치본에 적용할 함수명과 인자명은 업무 GPT가 실제 계약에서 찾아요.

| 단계 | Qwen이 맡을 한 단위 | 다음 단계로 넘길 근거 |
|---|---|---|
| V0 · 입력 고정 | 기존 Work·영수증을 확인하고 2절의 코드 폴더, Seed CL/PR, 현재 대상 revision·빌드 옵션·선택 파일과 탐색 예산을 고정 | 재사용할 결과, 이번 조회 범위, 미확인 항목 |
| V1 · Seed 전후 | Git은 실제 landing과 부모, P4는 변경 파일별 전후 revision을 대조. Jira·PR 주장과 코드·시험 사실을 구분 | 증상, 발생 전제, 원인, Fix 효과 및 적용 한계. 복수 원인은 분리 |

Seed 위치에 Fix가 들어간 경우에도 다른 후보의 조사는 계속해요. 원 수정을 같은 위치에서 빠뜨린 경우와 다른 경로의 변형을 구별해요. 신규 후보와 원래 Jira의 관계는 ‘같은 원인 규칙의 근거’로 기록해요.

### Qwen에 한 번에 주는 질문과 회수할 답

| 입력에 넣을 것 | 답에서 확인할 것 |
|---|---|
| 원인 규칙 하나, 대상 revision·빌드, 후보 함수의 관련 분기·return·정리, caller/callee 또는 wrapper의 보호 근거, 정상 반례 하나 | “같은 작업의 첫 잘못된 통지나 상태 사용 전에 이 보호가 효력을 내는가?”에 대한 판정, 지지·반대 근거 위치, 결정적인 미확인 경계 하나 |
| callback·IPC·간접 호출이 있으면 등록부와 전달부, 객체·세대 또는 Stack/domain/CC를 잇는 근거 | 같은 작업이라는 근거와 순서 보장 수단. 순서가 열려 있으면 필요한 등록부·호출부·기존 trace 중 다음 조회 하나 |
| 실제 조회한 범위와 남은 후보, 사용 가능한 시간·입력 예산 | 추가 조회로 새 근거가 생기면 해당 후보를 보강. 예산 소진·추가 근거 없음이면 확인 범위와 잔여 후보를 저장하고 재개 위치 기록 |

판정은 **이미 해결됨 / 발생 불가능 / 미해결 확인 / 추가 검증 필요** 중 하나를 사용해요. ‘이미 해결됨’에는 적시에 작동하는 동등 보호, ‘발생 불가능’에는 현재 빌드나 객체의 전제 불성립 근거가 필요해요. ‘미해결 확인’에는 같은 작업에서 입력→분기→위반이 이어지고 관련 보호가 위반을 막지 못하는 근거가 필요해요. 코드로 확인한 범위와 제품에서 관찰한 범위를 표시해요. 조사하지 않은 후보는 별도 집계해요.

### 한 Seed에서 누락과 오탐을 측정하는 방법

1. **기준을 먼저 고정해요(B1·D3).** 같은 소스 revision·빌드 조건·선택 파일·탐색 예산에서 담당자가 원본으로 확인한 기대 관계와 정상 반례를 먼저 기록해요. 첫 표본은 관련 함수 5개, 실제 메시지와 핸들러 등록 1~2건을 목표로 해요. 해당 형태가 없는 Seed는 적용 가능한 호출·보호 경계와 실제 개수를 기록해요. 같은 입력의 유효한 Work 결과를 먼저 재사용하고, Seed 보정용 입력과 별도 평가 사례는 구분해요.
2. **기존 probe를 대조해요(A1·B1).** 양방향 `callers/callees`, `dispatch`·callback 등 지원 action의 결과를 기준표에 맞춰요. 소스 파일 상한을 N개로 정하면 실제 내용을 읽은 서로 다른 제품 소스 파일 수와 선택 범위 밖 읽기 여부를 확인해요. 설정 파일·구조 메타데이터 읽기는 따로 세어요. 상한 초과, 근거 부재, 범위 잘림은 해당 범위를 부분 조사로 표시해요. 결과가 비거나 함수명이 같다는 사실만으로 발생 불가능·보호 충분을 확정하지 않아요.
3. **관계마다 결과를 남겨요.** 직접 호출, 정적 등록, 현재 빌드에서의 실행 가능성, 동일 작업의 비동기 순서를 구분해요. 근거가 있는 기대 관계의 적중·누락, 기대에 없는 관계 중 확인된 오탐, 확인할 수 없는 항목과 제외 사유를 분모와 함께 보고해요. 다른 도구와의 차집합은 추가 조사 대상으로 사용해요. 잘못된 확정, 확인된 필수 분기 누락, 잘못된 MSC 순서는 각각 0건이 수락 기준이에요. 품질 비율·시간 목표치는 대표 사례 실측 후 정해요.
4. **확장은 측정 결과로 결정해요(B2·B3).** 관련 빌드의 등록 테이블이 실제 존재하고 기존 경로가 특정 형식의 `메시지 ID → 핸들러`를 놓치면 그 형식에만 좁은 규칙과 반례를 추가하는 방안을 검토해요. 일반 인자 목록·동명 함수·비활성 분기를 대조하고 정적 등록 사실만 확정해요. 기존 탐색과 좁은 규칙으로도 필요한 관계를 반복해서 놓칠 때만 승인된 소규모 tree-sitter/SQLite 파생 캐시를 별도 평가해요. 추가 적중·오탐, 구축 시간·크기, 동일 입력 재구축, revision·build·규칙 변경 시 무효화를 확인해요. 효과가 없으면 기존 분석 경로를 사용해요. 첫 사례와 누락 측정은 파서·캐시 설치 없이 진행할 수 있어요.

## 4. 놓치는 사례에서 해결안을 고르는 기준

**합성 C++ 사례의 판정을 가른 것은 상위 통지 시점이었어요.** 두 실패 경로 모두 RF 자원을 반납했어요. 한 경로는 HAL 실패를 확인하고 실패를 한 번 통지했고, 다른 경로는 HAL 호출 후 결과를 분기하기 전에 성공을 한 번 통지했어요. 두 번째 경로에서는 자원이 정리돼도 상위는 성공으로 진행할 수 있어요. 아래 조치는 업무 GPT가 실제 계약에 맞춰 채택할 설계 후보예요.

| 후보에서 확인한 조건 | 해결 방향 | 수락할 증거 |
|---|---|---|
| HAL의 동기 실패 반환이 있고 성공 통지 시점을 옮길 수 있음 | 반환을 판정한 뒤 성공/실패로 분기. 성공은 정상 완료를 한 번 통지. 실패는 해당 작업의 소유자가 획득분만 정리하고 실패를 한 번 통지 | 성공·실패 양쪽에서 최종 통지 종류·횟수, 자원 상태, 상위의 최종 상태를 함께 관찰 |
| 비동기 요청 접수와 실제 완료가 분리됨 | API가 의미하는 접수·완료를 먼저 정의. 최종 성공은 같은 작업의 완료 근거 뒤에 확정하고, 지연·중복·이전 세대 응답을 기존 식별 규칙으로 처리 | 정상 지연에서 오판 없음. 이전 작업의 완료가 새 작업으로 귀속되지 않음 |
| 이미 최종 성공이 전달돼 상위 상태가 바뀜 | 잘못된 통지를 예방하는 수정을 우선. 이미 전이한 작업은 상위 소유자와 기존 취소·상태 재동기화 계약을 조사. 안전한 정정 수단이 없으면 상위 이관 또는 국소 복구 보류 | 실패 통지를 무조건 덧붙여 이중 종료하지 않음. 상·하위 상태 일치와 다음 정상 요청이 가능한지 확인 |
| 정적 위반은 보이지만 런타임에서 실패와 정상 중간 상태를 구별할 신호가 없음 | 부작용 전 검사·원인 수정을 우선. 필요한 관측값·시점·소유자를 지정하고, 신뢰할 판별 근거가 생길 때까지 자동 복구 보류 | 정상 반례를 오인하지 않고 관측값이 확보될 때 오류를 구분. 근거가 없으면 무엇을 관측해야 하는지 명시 |
| 실패 신호는 있으나 부분 HW 반영·공유 RF·타 Stack 영향 또는 소유권이 불명확 | 부분 적용 범위와 소유권 이전을 추적. 권한 있는 기존 소유자에게 전달하고 국소 정리·재시도의 안전 범위 결정 | 실제 획득분만 한 번 정리. 중복·release·경쟁, 복구 자체 실패, 다른 Stack 및 다음 요청 확인 |
| 분석기가 다른 함수를 진입점으로 골랐거나 MSC 순서가 코드와 다름 | 대상 함수의 분기·반환과 caller/callee 근거를 다시 확인. Recovery가 검증한 순서로 시나리오 입력을 고친 뒤 필요한 변환만 재실행 | 선택한 진입점·코드 위치·조건이 일치. 근거 없는 비동기 순서는 미확인. 순서를 뒤집은 대조 입력 검출 |

국소 복구를 제안할 때는 **검출 신호 → 정리 권한 → 부분 부작용 → 종료 통지 → SW/HW 복귀 확인 → 복귀 실패 시 이관**을 한 경로로 설명해요. 제품 변경으로 이어질 때는 기존 실시간 요구와 고정 자원 규칙(`new/delete` 금지)을 적용해요.

## 5. 두 필수 생산자 호출과 기존 Work 인터페이스

1. **`code-analyzer` 실제 호출.** Recovery가 고정된 소스와 대상 심볼로 기존 action을 호출해요. 생산자 버전·action·입력 revision/범위·실제 결과·실패 상태·파일/함수/분기 근거를 기록해요. 평가에 사용한 `v0.15.5` 개발 후보는 합성 함수 6개를 찾았지만 `--focus latePath`를 주어도 기본 진입점이 `releaseRf`였어요. 요약이 비어 있으면 함수별 사실과 실제 소스를 대조하고, 핵심 경계를 찾지 못하면 판정을 보류해요.
2. **MSC 입력 검증.** Recovery가 Seed 수정 전·후, 현재 후보 AS-IS, 제안 조치 TO-BE를 구분해요. AS-IS의 발신·수신·순서·분기는 각각 원본 revision과 근거에 연결해요. 비동기 순서는 이벤트 대응 근거가 필요해요. Edge의 의미·생성 조건·근거 표시는 업무 GPT가 기존 Recovery 계약에서 확정해요. 정의가 미확정이면 Edge 자체와 Edge에 의존하는 출력 요소를 미확정으로 표시하고, 해당 요소의 의미나 연결을 추정하지 않아요. 노드·발신/수신·순서 등 Edge와 무관하고 근거가 검증된 MSC 요소는 생성·변환을 진행해요. Edge 때문에 전체 시나리오를 올바르게 표현할 수 없는 부분은 해당 부분의 보류와 이유를 남겨요. TO-BE에는 제안임을 표시하고 조치가 없으면 해당 없음과 이유를 남겨요.
3. **`doc-converter` 실제 호출.** 검증한 시나리오 입력과 지원 action으로 변환하고 버전·입력 해시·결과/영수증을 남겨요. 합성 시험에서 `v0.2.26`은 순서를 뒤집은 입력도 형식 검증을 통과시켰어요. 변환 전 의미 검증과 변환 후 결과 대조가 모두 필요해요. 원본 PlantUML·SVG·B형 HTML 각각의 생성 여부와 상대 링크·해시를 기록해요. 변환 후 순서·방향·메시지 대응과 근거를 대조해 불일치하거나 검증할 수 없음이 확인되면 해당 미검증 MSC의 등록·링크·완료 판정을 차단해요. 실패 근거와 원본 입력은 같은 Work에서 보존하고 4절의 시나리오 입력 검증으로 돌아가 필요한 변환만 다시 실행해요. 이미 검증된 다른 산출물과 코드 분석 근거는 재사용해요.
4. **같은 Work에 전달·등록 확인.** 기존 승인 Work/Evidence writer의 preview→원본 SHA·Evidence revision 고정→등록→재조회 계약을 소비자로서 사용해요. 11월 24일 개발 계약은 `provider=l1-channel-recovery`, `kind=recovery_analysis`, `stage=utility`이며 활성 설치본과 대조해요. Recovery는 보고서·검증된 MSC 참조·출처를 제공하고 등록 응답·Evidence ID·재조회 상태를 기록해요. utility 첨부는 기술 분석·제품 검증 완료를 뜻하지 않아요. `RECOVERY.md`·`index/recovery.json`·`recovery/` 파생 보기와 저장 무결성은 Kernel 책임, 목록→사례→Work→HTML/SVG 열람은 Viewer 책임이에요. Recovery가 파생 파일을 직접 쓰거나 Viewer를 제어하지 않아요. 저장·실제 열람은 별도 통합 결과로 회수해요.
5. **부분 실패와 재개.** Recovery 분석 완료에는 Analyzer 실제 호출·원본 근거 대조·후보 판정이 필요해요. MSC 완료에는 별도 Converter 실제 호출 및 의미 검증이 필요하며 변환할 사실이 없으면 해당 없음/미확인 이유를 보존해요. 입력·버전·revision이 일치하는 유효 영수증은 재사용해요. 렌더러 누락은 Converter 단계, 저장 충돌은 기존 writer/Kernel 단계, 링크 누락은 읽기 연결/Viewer 단계에서 담당자가 재개해요. 변환 후 의미 대조 실패는 해당 시나리오 입력·근거를 재검증하고 필요한 변환만 재실행해요. 의미 검증을 통과한 결과만 등록·링크해요. 저장/열람 실패만으로 검증된 분석이나 MSC를 재실행하지 않아요.

11월 24일 인계의 Viewer `v0.5.3`과 Kernel `v0.7.47`은 별도 개발 전달본이며 업무 호스트 설치를 보장하지 않아요. Workflow `v1.6.75`의 후보 두 개는 같은 버전 문자열이지만 ZIP 내용이 달라요. Recovery가 실제 의존하는 Work 조회·등록 경로의 활성본·해시·지원 action만 필요한 시점에 확인해요. N2: 매핑 불명확 시 의존 단계만 보류하고 입력·권한·보존 경로가 확인된 독립 분석은 계속해요. Viewer/Kernel 전체 설치 점검·수정·통합 시험을 Recovery의 선행 전체 게이트로 강제하지 않아요. 공통 컴포넌트는 별도 통합 인계의 담당자가 검증해요. 업무 소스·Work·권한은 허용된 업무 호스트에서 확인하고 공개 인계 저장소를 실행 의존성에 넣지 않아요.

### 확정 사실을 판정·MSC에 넘기는 기준(B4·C3)

| 확인 순서 | 통과 기준과 실패 처리 |
|---|---|
| 원본 대조 | 설치본의 원본 revision·발췌 검증기를 재사용해 revision·build 문맥·경로·문장 범위·심볼을 고정해요. 실제 문장에 어떤 호출·등록·조건이 있는지 대조해요. 구조 파일에 호출 양끝 이름과 유효한 줄 번호만 있거나 줄이 무관한 선언을 가리키면 해당 `CONFIRMED`를 강등하고 원래 출력과 이유를 Work에 남겨요. |
| Recovery 의미 판정 | `l1-channel-recovery`가 등록부와 전달부, 빌드 조건, 같은 객체·세대·작업, 보호와 첫 잘못된 통지의 선후 관계를 확인해요. 정적 등록, 런타임 도달, 비동기 순서의 각 주장에는 별도 근거가 필요해요. 남은 불확실성은 `INFERRED`·`UNKNOWN`으로 남기고, 그 관계에 의존하는 후보는 ‘추가 검증 필요’로 돌려요. |
| 서술·변환 | Qwen에는 해당 후보의 검증된 fact 참조·라벨·제약만 넘겨요. Recovery가 서술과 Scenario IR에서 참조가 실제 facts 안에 있는지, 의미·방향·판정 수준이 유지됐는지 재검사해요. 없는 참조, 근거 없는 승격, 역순은 해당 요소를 보류해요. 독립적으로 검증된 요소는 기존 5절 절차로 변환·재조회해요. |

### 단계별 책임과 확대 조건(C1·C2·D1)

첫 사례는 Analyzer의 결정형 추출, Recovery의 후보 판정, Converter의 변환을 순차 호출해요. 지식 후보화를 별도로 요청한 경우에만 `l1-knowledge-updater`가 검증된 사실을 이어받아요. Knowledge Workflow 인계 r0005는 K5.8/K6의 읽기 전용 조사·설계가 범위이고, Qwen 품질 인계 r0001은 권한이 있는 Updater 가이드·호출부 보완과 회귀가 범위예요. Recovery의 필수 생산자는 5절의 두 스킬이에요.

대표 1건의 분석·MSC 품질과 실패 단계 재개를 확인한 뒤 독립 시나리오 단위 병렬화를 검토해요. 실제 다중 Work 쓰기 확대 전에는 저장 충돌·재조회 계약을 별도로 검증해요. Viewer 열람 실패만으로 독립 분석 확대를 차단하지 않되 전체 E2E 완료는 주장하지 않아요. 시나리오별 입력·출력을 분리하고 중복 입력, 공유 Work 쓰기 충돌, 전체 시간·토큰 예산과 부분 실패를 시험해요. 파일 단위 OpenCode worker 검증 결과는 시나리오 동시 실행 수의 근거로 승계하지 않아요. 기존 Job·모델 재호출은 영수증으로 중복을 막고, 예약 활성화와 그룹 게시는 해당 권한 범위에서 별도로 판단해요.

## 6. 첫 수락 시험과 업무 GPT 회신

아래 판정은 논리적 시험/보고 단위이며 새 Kernel schema·필드·원장 또는 상태 머신을 요구하지 않아요.

| 판정 단위 | 수락 기준 | 책임 |
|---|---|---|
| Recovery 분석 | 입력·Seed·원본 근거·후보 판정·반례·복구 방안 및 Analyzer 실제 호출 | Recovery |
| MSC 산출 | Converter 실제 호출·파일·의미 대조, 해당 없음/부분 미확인 이유 | Recovery + Converter |
| Workspace 저장 | 기존 승인 writer 등록·SHA/revision·재조회 | Workflow/writer + Kernel |
| Viewer 연동 | 저장 결과의 목록·상세·Work/MSC 실제 열람 | Viewer/읽기 연결 (별도 통합) |
| 제품 효과 | 승인된 실제 제품 시험 결과 | 제품 담당자/업무 호스트 |

각각 PASS/FAIL/SKIP/NOT_RUN을 보고해요. 필요한 단계가 차단되면 원인·재개 지점을 별도로 기록해요. 전체 E2E PASS는 해당 통합 시험까지 성공한 경우에만 보고해요.

아래는 **업무 환경에서 수행할 시험 계획**이에요. r0004에서 인용한 11월 25일 Recovery 평가의 직접 시험 범위는 합성 C++ 성공·실패 4조합, Analyzer 함수·호출 근거 조회, Converter 형식 검증과 PUML 생성까지예요. 해당 Recovery 평가에서는 Analyzer의 호출 위치를 합성 소스와 대조해 Converter의 시나리오 입력을 별도로 작성했어요. PlantUML 렌더러가 없어 SVG·HTML은 생성되지 않았어요. 업무 Qwen 성능, 자동 연동, 제품 복구 효과는 아직 미검증이에요.

**후속 격리 시험에서 확인한 개발본의 한계.** 공개 `code-analyzer v0.15.5`의 선별 회귀는 62건 중 61 PASS, 설치 자체검사 1 FAIL이었어요. 호출 관계 9/9, 분석 정확도·저장 25/25, OpenCode 관련 27/28이었어요. ZIP의 `VERSION`은 `0.15.5`, `.skill-release.json`은 `0.15.4`, `install.py`의 기준은 `0.15.2`여서 임시 환경의 정식 설치가 `version_match=false`로 끝났어요. 이 후보의 설치·배포는 보류하고 현장 활성본으로 독립 가능한 시험을 진행해요. 이 결과는 활성 업무 설치본의 상태와 별도로 기록해요.

**최신 개발 후보 v0.15.6 참고:** [별도 Analyzer 인계](./CODE_ANALYZER_V0156_DEVELOPMENT_DELIVERY_r0001_20261125_KST.md)에서 버전 정합성과 단순 직접 호출 근거 보완, 격리 harness 13/13 PASS가 보고됐어요. 전체 회귀·설치 self-check·독립 리뷰·업무 호스트 검증은 NOT_RUN이며 development_not_for_deployment예요. 기존 활성본 유지, 신규 설치·자동 업데이트 금지예요. v0.15.5의 실패와 오탐은 해당 버전의 역사적 근거로 보존하며 v0.15.6의 효과를 추정하지 않아요.

같은 개발본의 합성 C++ 시험에서 무관한 선언 줄에 가상의 callee를 연결해도 `CONFIRMED`와 `unanchored_edge_count=0`이 나왔어요. 직접 `switch/case` 호출은 추출했고 포인터 멤버 등록 테이블 한 형태는 0건이었어요. 두 사례는 아래의 부정 시험에 쓰고, 실제 제품 경로의 누락 여부는 업무 기준표와 대조해요.

| 확인할 동작 | 시험 입력과 기대 결과 |
|---|---|
| 코드 폴더 선택 | 이번 지정 경로가 유효하면 저장값보다 우선. 경로 무효·프로젝트 불일치면 유효한 저장값이 있어도 경로 질문 1회, 응답 전 제품 소스 분석 0회. 지정이 없고 저장값이 유효하면 경로 질문 0회. 미설정·이동·권한 문제·복수 후보에서는 필요한 경로 확인 1회. |

| 후보 판정·범위 | 보정용 비-timeout Seed와 별도 평가 사례를 준비하고 C++ 담당자가 예상 판정을 먼저 고정. 알려진 미해결 후보, 상위 보호, 늦은 정리, 비활성 빌드, 불명확한 callback을 대조. 조사·미조사·보류 수와 분모를 함께 보고 |
| 검출 및 조치 | 4절의 성공/실패·기존 성공 통지·중복/지연·다른 소유자 사례에서 신호·통지 횟수·자원·상위 상태·다음 정상 요청을 검증. 자동 복구를 보류할 사례도 정답에 포함 |
| 분석·변환 | 진입점 불일치, 뒤집힌 MSC 순서, 미확인 메시지, 렌더러 누락 대조. 두 호출 영수증·실제 산출물을 확인하고 실패한 단계에서 재개 |
| 저장·Viewer (별도 통합) | Work 저장 충돌·Viewer 링크 누락을 담당 컴포넌트에서 확인. 분석·MSC 유효 결과 보존, 후속 실패만으로 모델/Job/Analyzer 재호출 0건. 저장·열람 별도 판정 |
| 변환 후 의미 검증 · N1 | Converter 형식 검증은 PASS이나 의미 대조에서 역순·방향 불일치 검출 → 문제 MSC 등록·링크 0건, Work에 실패 근거·입력 보존, 시나리오 재검증 및 해당 변환 재개. 보정본의 의미 검증 및 실제 파일 재조회 PASS일 때만 등록·링크. |
| 활성 Workflow 매핑 · N2 | 같은 v1.6.75 후보가 복수이고 실제 설치본 해시/지원 action을 확인할 수 없음 → 실제 의존 단계만 보류, 독립 분석 결과 보존 및 원인·재개 조건 기록. 매핑 확인 후 해당 단계만 재개. |
| Edge 미확정 · N3 | Edge 정의가 없는 검증된 시나리오 → Edge와 의존 요소는 미확정 표시, 독립적으로 검증된 노드·메시지·발신/수신·순서 등은 MSC 생성·변환. 미확정 부분을 사실처럼 렌더링하지 않음. 출력 의미 대조와 미확정 표기 확인. |
| Qwen 절차 비교 | 기존 방식과 새 방식을 같은 모델 설정·코드·빌드·사례·시간/토큰 예산에서 비교. 알려진 결함 누락·정상 오탐·근거 없는 확정·잘못된 MSC 순서·보류율·처리 비용을 기록. 첫 권장 수락 기준은 알려진 미해결 경로 식별, 대조 사례 기대 판정 일치, **근거 없는 확정과 잘못된 MSC 순서 각 0건** |
| 실제 읽기 범위 · A1 | N개 상한보다 많은 소스를 제공해 caller·callee 양방향 조회. 서로 다른 제품 소스 읽기 ≤ N, 범위 밖 소스 읽기 0건. 잘린 범위와 미조사 후보는 별도 집계. 확인할 수 없으면 해당 시험을 보류하고 대규모 확대를 보류. |
| 원본 근거·서술 · B4·C3 | 유효한 줄 번호가 무관한 선언을 가리키는 호출, 없는 fact 참조, 다른 빌드의 분기를 입력. 원본 대조 뒤 근거 없는 확정·해당 MSC 요소 등록 0건. 실제 직접 호출은 유지하고 영향받는 판정만 보류. |
| 등록과 실행 · B1·B3·D3 | 실제 등록과 인자가 비슷한 일반 호출, 직접 `switch/case`, 활성·비활성 빌드를 대조. 기준표와 probe의 적중·누락·오탐·미확인, 후보 분모를 회수. 등록만으로 런타임 도달이나 CNF 순서를 확정한 건수 0. |

업무 GPT가 먼저 회신할 결과는 **기존 구현과의 차이, Qwen에 줄 Recovery 변경 지침, 첫 시험의 입력과 예상 판정**이에요. 실제 실행 뒤에는 Work ID·대상 revision, 코드 경로 확인 결과, 후보별 근거·조치, 두 스킬 영수증, 산출물 등록 응답·재조회 및 별도 Viewer 열람 결과(미실행이면 NOT_RUN), 시험별 PASS/FAIL/SKIP/NOT_RUN 및 다음 한 행동을 같은 Work 또는 승인된 기존 보존 경로에 기록해요. 공통 컴포넌트 결손은 담당·근거·후속 조치로만 제시해요. 업무 소스·로그·상세 MSC는 허용된 업무 Work에 보존해요. 첫 사례 회신에는 실제 읽은 파일 수/상한, 기대 관계 수, 적중·누락·오탐·미확인 수, 원본 대조에서 강등한 수와 남은 `UNKNOWN`, 두 생산자 영수증 및 Work·Viewer 재조회 상태를 한 줄로 덧붙여 주세요.
